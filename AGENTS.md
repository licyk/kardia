# Repository Rules

- Any breaking refactoring is allowed; backward compatibility is not required. Do not add compatibility layers or retain obsolete interfaces solely to preserve existing behavior.
- Avoid excessive checks and overly strict field validation. Validate only what is necessary for correct operation, and tolerate unknown fields in configuration files and upstream data instead of rejecting otherwise usable input.
- Do not add complexity for speculative, extremely unlikely race conditions or security edge cases. If you believe such complexity is necessary, first explain exactly what could go wrong, how likely it is, and how much additional code it would require. Proceed only after I approve. Do not silently expand the scope of changes.
- Validate external data only once, at the entry boundary. Pass values of known types into internal code, and do not repeat defensive checks internally.
- Keep the main function focused on the normal flow. Put validation and implementation details in small helper functions below it.
- Write comments only for non-obvious constraints and counterintuitive behavior. Do not comment on self-explanatory code.
- Do not manually edit generated files. Change the source and regenerate them.
- Test the real implementation. Do not duplicate business logic in tests. Minimize the use of mocks.
- Follow the repository's existing workflows. Do not introduce tools or workflows the repository does not already use.
- Do not prematurely extract functions that are used only once. Extract a function only when it will be reused, encapsulates truly complex logic, or represents a concept that can be clearly named.
- Keep `lib.rs` and `mod.rs` as module entry points: they declare modules, re-export, and hold docs and attributes; implementation lives in a file of its own. `cargo xtask arch` checks this (proc-macro entry points and inline re-export-only modules are allowed).

## Mandatory plugin failure isolation and configurable recovery

- Every plugin implementation and refactoring must preserve failure isolation. A plugin error, unwind panic, failed background task, or isolated guest crash must not terminate the host or stop unrelated plugins. Only the failed plugin and consumers of its unavailable services may be interrupted; independent plugins must continue serving requests and making progress throughout the failure and recovery.
- Recovery policy must be configurable by the user: automatic retry, remaining failed until manual intervention, or host-defined handling. Do not force automatic recovery or restart. Document the default and honor the selected policy; failure isolation and continued operation of unrelated plugins are mandatory under every policy. These are implementation and acceptance requirements, not a claim that every existing plugin already exposes all three policies.
- When automatic retry is selected, supervision must outlive the failed instance, use the lifecycle's supported recovery operation, and retry at a bounded rate. Explicit disposal, disabling, or removal must cancel pending recovery. Invalid configuration must be reported rather than retried unchanged. Manual mode must not retry on its own; host-defined handling must receive the failure and control the response, with handler errors contained so unrelated plugins remain operational.
- Distinguish a request or connection failure from an instance failure. Contain the former to that operation when the plugin remains usable; withdraw a failed instance's services, clean up its effects, and apply the selected recovery policy when it no longer works. Do not silently swallow a dead task's failure or reset the root context to recover one plugin.
- Bind routes, listeners, sockets, streams, child processes, and background tasks to their owning lifecycle. Recovery must finish the failed instance's cleanup before replacing it, without duplicate registrations, leaked resources, or stale tasks acting on the replacement. Execute user callbacks and asynchronous cleanup outside runtime locks.
- Verify all three recovery policies with fault injection against the real implementation while independent plugins keep working. Automatic retry must recover without test-driven restart/update calls; manual mode must remain failed until explicitly handled; host-defined mode must follow the host's decision and contain handler failures. Repeat failure and recovery to check cleanup, and verify that disposal cancels pending recovery. Cover relevant native platforms; mocks, compilation, and a successful host restart do not establish isolation or recovery.
- State the actual containment boundary. In-process unwind handling cannot contain `abort`, segmentation faults, or process-wide termination; plugins requiring isolation from those failures must use the existing process or WebAssembly boundary as applicable. Do not describe native dynamic libraries as crash-isolated. Preserve existing guest failure reporting and panic-containment behavior when changing shared infrastructure.
