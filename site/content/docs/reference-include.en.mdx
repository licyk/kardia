This page covers `cordis/packages/include/src/{index,journal,patch}.ts` and `packages/group/src/index.ts`. The paper counterpart is §5.2.1 ("`@cordisjs/include` loads an external configuration file (YAML or JSON) and grafts its entries in as a nested subtree", see [Implementation](/docs/concepts-implementation)). The paper does not describe the synchronization machinery below; it is an implementation contribution.

## Group [#group]

`packages/group/src/index.ts` only re-exports `Group` from the loader (see [`EntryTree` and `EntryGroup`](/docs/reference-loader#entry-tree)). Its config is the list of child entries; config updates are absorbed in place as a keyed diff.

## Include: a file-backed `EntryTree` [#include]

`class Include extends EntryTree`, with `inject = ['loader']`, used as:

```ts
{ name: '@cordisjs/plugin-include', config: { path, initial?, patches?, enableLogs?, watch? } }
```

It is a class plugin whose async-generator `[Service.init]` reads the file, yields `() => this.stop()`, and applies the tree. Its entries' composite ids are `<includeEntryId>:<localId>`; includes nest.

- `path` resolves against the parent tree's `baseUrl`; the include's own `ctx.baseUrl` becomes the file's directory (nested names and includes resolve relative to the file).
- `initial` is written if the file does not exist (ENOENT only); an unparsable existing file is **never overwritten**.
- `watch: true` → `ctx.inject(['fs'], ctx => ctx.fs.watch(filename).on('change', () => this.refresh()))`.
- An `internal/update` listener reconfigures in place (new `patches`) unless `path`/`watch` changed (then it does a full restart).

### State [#state]

| Field | Meaning |
|---|---|
| `filename` | the resolved file |
| `type` | `application/json` or `application/yaml`, by extension |
| `cache?` | `{ content, data (parsed, ids assigned, unpatched), syntax? }` |
| `journal` | `Map<id, JournalRecord>`: tree-side changes not yet in the file |
| `index?` | `PatchIndex` (ownership) |
| `anonymous` | ids invented for id-less file entries |
| `dirtyRead` / `dirtyWrite` | IO flags |
| `_draining` | the running IO loop |
| `_pendingTree` / `_applyTask` | latest-wins application |

## The IO loop [#io-loop]

`index.ts:365-397`. A single-flight `_drain` runs `while (dirtyRead || dirtyWrite) { read-if-dirty; write-if-dirty }`. Read errors are **warnings** (half-written files are routine while editing) and stop the loop without writing (the file state is unknown); write errors are logged and the loop continues. `commit(change)` (from the tree) records into the journal, sets `dirtyWrite` and drains. `refresh()` (the watcher) sets `dirtyRead`.

### `_read()` [#read]

1. Read; identical content ⇒ no-op (this also suppresses watcher feedback from its own writes).
2. Parse YAML (core schema regardless of `%YAML`, custom tag `!!js`, **errors and warnings both fatal**) or JSON; map issues to `file:line:col` (1-based, **UTF-16 columns**).
3. Validate the top-level array and the object entries; on failure keep the previous tree.
4. Assign ids to anonymous entries (stable across reads: the previous id is reused if the parent is the same and the options are deep-equal).
5. If this is not the first read: a three-way **reconcile** of the journal against the old and new file states; the **file wins** on conflict, and each conflict is logged.
6. Cache and schedule an apply; if the journal is non-empty, schedule a write.

### `_write()` [#write]

- Re-read; if the file changed externally, merge first.
- Snapshot-and-swap the journal; `routeJournal` sends each change to its **owner**: the file data, a patch in the include's own config, or an entry embedded in a patch.
- Patch changes are persisted by `this.ctx.fiber.update(newConfig)` (not awaited), which flows through `internal/commit` into the **parent** tree's file.
- File changes are dumped (**whole-file regeneration: comments and formatting are lost**) and written atomically: a temp file `.<base>.<pid>.<seq>.tmp` in the same directory, a stale-content check before **every** rename attempt, and rename with retries on EACCES/EPERM/EBUSY (11 attempts, linear backoff).
- Read-only files keep changes in memory, with a warning.

### Tree application [#apply]

`applyPatches(cache.data, patches)` (a fresh clone every time, so removing a patch reverts it) → `applyJournal(data, journal)` (overlay unwritten runtime changes) → latest-wins `root.update(tree)` → `EntryGroup` keyed reconciliation.

## Journal [#journal]

`journal.ts` contains pure functions:

```ts
type JournalRecord =
  | { kind: 'remove' }
  | { kind: 'upsert'; created: boolean; parent: string | null | undefined; position: number; changes: Dict }
```

| Function | Purpose |
|---|---|
| `record` | deltas captured at report time |
| `mergeRecords` | remove∘created-upsert = nothing; upsert after remove ⇒ `created:false`; changes merged newer-wins |
| `flatten`, `applyChanges`, `detach`, `place`, `applyJournal` | apply records to entry lists |
| `reconcile(journal, base, theirs, fileOwned)` | the three-way merge, where conflicting keys/moves/removals are dropped from the journal ("file wins") |

## Patches [#patches]

`patch.ts`:

- An **insert patch** `{ id?, insert: [...] }` appends entries into a group (or the root).
- An **override patch** `{ id, name?, ...keys }` overrides keys of an existing entry. `name`, if given, must match (a guard against patching a different plugin); overriding a group's `config` replaces its child list.
- `applyPatches` builds a `PatchIndex` recording the **owner** of every entry and key: `file`, `patch{index}` or `embedded{index, key}`. Later patches can address entries inserted by earlier ones.
- `routeJournal` writes each runtime edit back to its owner: patch-owned keys → the patch; entries inserted by a patch → inside the patch; the rest → the file.

## Source locations [#source-locations]

`_route(id, path)` finds where a value is written (file, patch, embedded) and delegates up through nested includes, producing virtual stack frames like `at a (inner.yml:1:3)` / `at inc (middle.yml:1:3)`. `walk` descends the YAML AST (resolving aliases to anchors); `seekExpr`/`scanScalar` map an offset inside an expression to a file offset (decoding quoted-scalar escapes).

## Design notes [#design-notes]

- The include is the clearest example of the paper's *bidirectional* binding between configuration and fibers: runtime changes (plugin self-update or self-disable, API edits) flow back into files, file edits flow into fibers, and conflicts are resolved deterministically.
- Correctness relies on confluence (Theorem 80, see [Metatheory](/docs/concepts-metatheory)): the include may apply intermediate trees, skip them (latest-wins) or apply them in a different order; the quiescent state depends only on the final tree.
- The synchronization core (journal, patch, reconcile, routing, id assignment) is **pure data transformation** over entry lists and is the most portable part of the code base.
