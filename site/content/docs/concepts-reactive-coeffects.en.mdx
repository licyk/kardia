This page summarises §3.2 of the paper ([arXiv:2608.25512](https://arxiv.org/abs/2608.25512)). Definition numbers are the paper's. For the Cordis realisation see [Context and reflection](/docs/reference-context) and [Fiber lifecycle](/docs/reference-fibers) in the Cordis reference.

Spatial composability is the ability of components to declare dependencies and of the system to resolve, provide and withdraw them at runtime. Dependency satisfaction must be re-evaluated whenever the shared context changes, so that a component activates when its dependencies become available and deactivates when they are withdrawn.

## Coeffect context (§3.2.1)

The paper formalises an inversion-of-control (IoC) container as a coeffect context.

### Definition 19 – coeffect context

For a type family `𝒱 : K → Type`, `Σ := (k : K) ⇀ 𝒱_k` is a **finite dependent partial function**. Notation: `σ(k)` application, `σ[k ↦ v]` extension, `σ ∖ k` restriction, `k ∈ dom(σ)` membership. The type family gives each key a static value type.

**Preconditions:** a dependency may not be provided twice (`k ∉ dom(σ)` for extension) nor revoked if absent (`k ∈ dom(σ)` for restriction). A violated precondition is *signalled as an error and produces no transition* (equivalently, compose in the `Maybe` monad).

### Definition 20 – get / set

```text
get : (k : K) → Σ ⇀ 𝒱_k                     get(k)(σ)    = σ(k)                 requires k ∈ dom(σ)
set : (k : K) × 𝒱_k → Σ ⇀ Σ × (Σ ⇀ Σ)       set(k, v)(σ) = (σ[k ↦ v], λσ′. σ′ ∖ k) requires k ∉ dom(σ)
```

`set(k, v)` **is an effect function** (`𝔈Σ*`). The effect machinery of §3.1 ([Revertible effects](/docs/concepts-revertible-effects)) therefore applies directly: dependency registrations are tracked and recovered automatically. *"Coeffect operations are effects, and effects are revertible."*

## Specification and notification (§3.2.2)

Accessing an absent dependency is a runtime failure, so a component should **activate only once all its declared dependencies are present**, instead of accessing them optimistically.

- **Satisfaction predicate**: `σ ⊧ d := ∀k ∈ d. k ∈ dom(σ)`, decidable because `dom(σ)` is finite.
- Because every mutation of `σ` passes through effect functions, changes of satisfaction are detectable at each effect boundary: *the effect system guarantees that every coeffect change is observed.*

### Definition 21 – coeffect specification

`𝔇Σ := Set(K)`.

### Definition 22 – notification

```text
notify_d(σ, σ′) = activating    if σ ⊭ d ∧ σ′ ⊧ d
                  deactivating  if σ ⊧ d ∧ σ′ ⊭ d
                  neutral       otherwise
```

An activating transition triggers execution of the component's effects (tracked as in §3.1); a deactivating one triggers recovery through the accumulator.

**Local spatial composability**: a component activates only at a state satisfying its specification (it never reads an absent binding), and every context change is classified against the specification (loss of satisfaction is detected where it happens). Two things are left to the global form (§4.3.3, see [Metatheory](/docs/concepts-metatheory)): withdrawing a binding only *after* the deactivations it causes have finished, and keeping the bindings an activation reads unmoved while it runs.

## Isolation and interception (§3.2.3)

The flat table cannot bind *different* values to the same logical dependency for different components. The paper adds two extensions.

### Realization (Definition 23)

An effect function on a context admits two realizations:

- **In-place**: mutate the context and return a non-trivial inverse; recovery runs the inverse.
- **Derived**: leave the input intact and return a *fresh context deriving from it* with the identity inverse; recovery discards the derived context.

In a purely functional setting the two coincide; an imperative host may choose per operation. **Isolation and interception are given derived realization**: they produce a child context whose own table differs from the inherited one, leaving the shared table untouched, so there is nothing to track. Assignment on a derived table overrides the inherited one at that key, so neither operation has a precondition.

### Coeffect isolation – Definitions 24, 25

```text
Σ_iso := (K ⇀ R) × ((r : R) ⇀ 𝒱_r)        a pair (ρ, σ)
ρ : realm table; a key outside dom(ρ) resolves to its own realm (ρ(k) = k, R ⊇ K)
σ : dependency table indexed by realm

get(k)(ρ, σ)       = σ(ρ(k))
set(k, v)(ρ, σ)    = ((ρ, σ[ρ(k) ↦ v]), λ(ρ′, σ′). (ρ′, σ′ ∖ ρ′(k)))
isolate(k, r)(ρ,σ) = (ρ[k ↦ r], σ)          -- derived; reassigns rather than refuses
```

The two-layer resolution `k → ρ(k) → σ(ρ(k))` decouples the logical layer from storage. The paper describes this as **runtime ad-hoc polymorphism**: the same key resolves to different values in different contexts, adjustable at runtime (multi-tenant systems, testing, sandboxes). `set` remains an effect function (revertible); `isolate` needs no inverse.

### Coeffect interception – Definitions 26, 27

Interception attaches cross-cutting **metadata** to dependency access without changing the value.

```text
Σ_inter := ((k : K) → ℳ_k) × ((k : K) ⇀ (ℳ_k → 𝒱_k))      a pair (ι, σ)
𝔇_inter := (k : K) ⇀ ℳ_k                                   specification carries metadata
Each key has a metadata monoid (ℳ_k, ⊕_k, ε_k).

get(k, μ)(ι, σ)       = σ(k)(μ ⊕_k ι(k))
set(k, ψ)(ι, σ)       = ((ι, σ[k ↦ ψ]), λ(ι′,σ′). (ι′, σ′ ∖ k))
intercept(k, ν)(ι, σ) = (ι[k ↦ ι(k) ⊕_k ν], σ)        -- derived
```

- `ι` is the **context-carried** metadata (installed by an enclosing context); `σ(k)` is a *provider function* from metadata to value; the specification `d(k)` is the **component-declared** metadata.
- On access the system evaluates `σ(k)(d(k) ⊕_k ι(k))`. The merge follows each key's semantics (scalars overwritten, sets unioned) and is **right-biased**: context-carried metadata wins, so an enclosing context can constrain how a component uses a coeffect without modifying the component (used for access control in §6.3, see [Discussion and related work](/docs/concepts-related-work)).

## Engineering take-aways

| Formal notion | Practical reading |
|---|---|
| `Σ` as dependent partial map | A service registry keyed by name, each key with a fixed value type. |
| `set` precondition | Providing an already provided key is an error ("single source"). |
| `set` is an effect | `provide(name, value)` returns a disposer and is tracked by the enclosing scope. |
| Satisfaction / notify | A consumer is started only when every injected key is available; every provide/withdraw re-evaluates affected consumers. |
| Derived realization | `ctx.isolate(...)` / `ctx.intercept(...)` return a *new child context object*; there is nothing to undo. |
| Realm | An opaque token per (scope, key); the same token means a shared binding. |
| Interception merge | Declared metadata (in the consumer's `inject` declaration) merged with context metadata; outer → inner, inner wins. |

<Callout type="info">
**In kardia:** a key is the string `Service::NAME` bound to a Rust type through the `Service` trait. `ctx.provide(value)` is a tracked effect returning an `EffectHandle`, and providing a key twice in one realm fails with `KardiaError::AlreadyProvided`. `ctx.isolate(key)` (a fresh private realm), `ctx.isolate_in(key, realm)` (a shared realm) and `ctx.intercept(key, meta)` return a derived `Context`. Declared metadata comes from `Inject::with_meta`, and `Service::merge_intercept` merges it with the context's, outermost first, by default a right-biased shallow merge of JSON objects. See [Services](/docs/guide-services).
