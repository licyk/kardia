**访客插件**（guest plugin）是 [`hmr` 插件](/docs/guide-hot-reload)可以原地重载的独立模块；编译进二进制的插件则不同，修改其代码需要重启。在 `kardia` 二进制加载的配置文件中，任何不是内置插件的条目名都是访客模块路径，相对于配置文件：

```yaml
- id: hello
  name: ./plugins/hello.wasm
  config: { greeting: hi }
```

所有后端都使用同一套基于 JSON 的**访客 ABI**（见下文），并通过一个桥接插件运行每个访客插件：桥接插件为每个纤程（fiber）实例化一次访客，并在纤程被释放（dispose）时丢弃该实例。Rust SDK `kardia-guest` 可以用同一份源码为所有后端编写这样的访客。

## 后端 [#backends]

| | WebAssembly（`WasmSource`） | 动态库（`DylibSource`） | 子进程（`ProcessSource`） |
|---|---|---|---|
| 文件 | `.wasm`，或 `.wat` 文本 | `.so` / `.dylib` / `.dll` | 可执行文件 |
| 运行方式 | 在 wasmtime 上，每个纤程一个 store | 在宿主（host）进程内 | 每个纤程一个子进程 |
| 隔离 | 沙箱，可选燃料、时间和内存限制 | 无：库中的崩溃会使整个应用崩溃 | 崩溃的访客只会让它自己的插件失败 |
| 重载 | 每个版本编译一次；新旧实例并存，丢弃实例会释放其全部内存 | 每个版本从一份新副本加载，**永不卸载**；一直保留到进程退出 | 重载模块会重新启动其进程 |
| 适用于 | 生产环境的访客 | 开发：同一套工具链，无需 WASM 目标 | 任意语言编写的访客，或不能让宿主崩溃的访客 |
| `kardia` 二进制 | 支持 | 支持 | 暂不支持（仅限库） |

**WebAssembly。** `WasmSource` 在 wasmtime 上运行核心 WebAssembly 模块，而不是 WIT 组件，因此访客不需要组件工具链（测试用 WAT 编写）。模块每个版本编译一次，并为每个纤程在各自的 store 中实例化。`WasmSource::with_limits` 为每个实例设置上限：

```rust
use kardia::hmr::{WasmLimits, WasmSource};

let source = WasmSource::with_limits(
    WasmLimits::new()
        .fuel(10_000_000)                    // per export, about one unit per instruction
        .timeout(Duration::from_secs(5))     // per export, by epoch interruption
        .memory(64 << 20),                   // the most linear memory, in bytes
);
```

燃料或时间耗尽的导出会触发陷阱（trap），该实例之后的调用以 `the guest was stopped: …` 失败；内存增长超过上限也会触发陷阱。设置了时间上限时，调用者自己的截止时间（[`call_timeout`、`call_async`](#guest-service)）同样生效。`WasmSource::new()` 不设置任何上限。这些失败都是带类型的 [`GuestFailure`](#guest-failure)。

要像 `ProcessGuest::plugin` 那样从外部给出 WASM 插件的元数据，可以把模块编译为 `WasmGuest`：`WasmGuest::new(bytes, limits)` 在自己的引擎上编译 WASM 字节或 WAT 文本，`source.guest(bytes)` 则在某个 `WasmSource` 的引擎上、按它的上限编译。两者都不实例化模块。`plugin(meta)` 生成插件，每个实例启动时必须声明相同的元数据；`module(id)` 则像 `WasmSource` 那样从一个实例中读取元数据。

```rust
use kardia::hmr::{GuestMeta, WasmGuest, WasmLimits};

let guest = WasmGuest::new(std::fs::read("greeter.wasm")?, WasmLimits::new().fuel(10_000_000))?;
let plugin = guest.plugin(GuestMeta::new("greeter").provide("greeter"));
```

**macOS 上的陷阱处理**。在 macOS 上，wasmtime 默认通过 Mach 异常端口处理 WASM 陷阱。它的陷阱处理器是进程级的：wasmtime 在创建第一个引擎时安装它，之后的引擎若要求另一种设置，wasmtime 会 panic。`kardia::hmr::set_macos_mach_ports(false)` 让 kardia-hmr 创建的每个引擎改用 Unix 信号。请在创建第一个 `WasmSource` 或 `WasmGuest` 之前调用它：此后再要求另一种设置会返回错误，且不改变任何东西。应用自己用 wasmtime 创建的引擎必须使用相同的设置。在 macOS 以外的平台上，这个调用不改变任何东西。

**动态库。** `DylibSource` 使用 C ABI，而不是传递 Rust 类型：`cdylib` 自带一份 `kardia-core` 和 tokio，静态变量各自独立，也没有运行时上下文。每次加载都会把库复制到一个新路径（位于临时目录下的 `kardia-dylib-<pid>` 目录中），因为平台加载器对已知路径会直接交出已加载的那个库。库永不卸载：一旦 Rust 代码注册了线程局部析构函数或交出了 `'static` 引用，卸载它就是不健全的。

**子进程。** `ProcessSource` 把每个插件实例作为独立进程运行，通过 stdin 和 stdout 以 JSON 行的形式使用访客 ABI（见[进程传输](#process)）。进程结束的访客只会让它自己的插件失败；破坏协议或超过调用截止时间的访客会被杀死。命令行参数、spawner、超时和退出报告见[进程访客](#process-guests)。替换可执行文件时，请把新文件重命名覆盖到原路径：正在运行的可执行文件不能被写入，而以写方式打开着的文件不能被启动。

**三者的共同点。** `GuestService::call` 会阻塞调用者直到访客应答；`call_async` 则在异步工作线程之外执行调用，桥接插件执行 `apply` 和 `dispose` 时也是如此。截止时间可以终止进程访客（将其杀死）和设置了时间上限的 WASM 访客（触发陷阱）；dylib 访客运行在调用者的线程上，无法被终止。没有单独的代理（broker）服务：每个纤程的 `GuestService` 就是 RPC 端点。这些后端是 `kardia-hmr` 的 cargo 特性（`wasm`、`dylib`、`process`，默认全部开启）；另有 `preserve-order`（默认开启），它通过 `kardia-loader` 开启 `serde_json/preserve_order`，关闭它可让应用保留 serde_json 的默认映射（[键顺序](/docs/development-loader#loader)）。

`kardia` 二进制按文件扩展名选择后端：`.wasm` 和 `.wat` 交给 `WasmSource`，其他一律交给 `DylibSource`。基于库构建的应用可以自行选择：

```rust
use kardia::hmr::{DylibSource, ModuleCode, ModuleSource, ProcessSource, WasmSource};

/// Guest modules by extension: WASM, executables in `bin/`, else a dynamic library.
struct GuestFiles {
    wasm: WasmSource,
}

impl ModuleSource for GuestFiles {
    fn load(&self, id: &str) -> Result<ModuleCode> {
        let path = Path::new(id);
        match path.extension().and_then(|ext| ext.to_str()) {
            Some("wasm" | "wat") => self.wasm.load(id),
            _ if path.parent().is_some_and(|dir| dir.ends_with("bin")) => ProcessSource.load(id),
            _ => DylibSource.load(id),
        }
    }
}

let graph = ModuleGraph::new(GuestFiles { wasm: WasmSource::new() });
```

## 从 Rust 调用访客 [#guest-service]

访客通过 `Host::provide` 提供服务。在宿主一侧，每个这样的服务都是一个 `kardia::hmr::GuestService`，其 JSON 视图就是访客提供的值：

```rust
use kardia::hmr::GuestService;

let counter = ctx.get_as::<GuestService>("counter")?;     // checked access, by key
println!("{}", counter.value());                          // the provided JSON value
let count = counter.call("increment", json!(null))?;      // calls the guest's `call`
let view = ctx.view("counter")?;                          // the JSON view alone
```

| `GuestService` | |
|---|---|
| `value()` | 访客提供该服务时给出的 JSON 值 |
| `call(method, args)` | 以 `{ key, method, args }` 调用访客的 `cordis_call`，返回其 JSON 结果；阻塞直到访客应答，或直到访客的默认超时 |
| `call_timeout(method, args, timeout)` | 与 `call` 相同，但超过 `timeout` 后以 `the guest did not answer in time` 失败；此时进程访客会被杀死，之后的调用也会失败 |
| `call_async(method, args, timeout)` | 在异步工作线程之外执行调用，可设置超时；丢弃该 future 即取消调用（`kardia-guest/2` 访客会收到通知，其结果被丢弃） |
| `is_available()` | 实例是否仍能应答：未被释放，且其进程没有退出 |
| `handle()` | 进程访客的 [`GuestHandle`](#exit) |

提供该服务的纤程消失后，调用以 `the guest instance is disposed` 失败；进程访客自行结束后，以 `the guest process exited` 失败；访客返回的不是 JSON 时，以 `invalid result of <key>.<method>: …` 失败。访客回调到一个已在同一线程上运行的实例（直接或经由其他访客）时，会以 `re-entrant call into a guest instance` 失败，而不会死锁。与任何服务一样，访客的纤程被释放时，访客服务随之撤回。

## 进程访客 [#process-guests]

`ProcessSource` 把模块 id 当作程序运行，不带参数。`ProcessGuest` 描述一条访客命令及其选项；可以直接使用，也可以在你自己的 `ModuleSource` 中使用：

```rust
use kardia::hmr::{GuestCommand, GuestMeta, ProcessGuest};

let guest = ProcessGuest::new(
    GuestCommand::new("python3").arg("plugin.py").env("PLUGIN_ROOT", &root).current_dir(&data),
)
.spawner(MySpawner)                          // default: StdSpawner
.timeout(Duration::from_secs(30))            // each export, unless its caller sets a deadline
.frame_limit(1 << 20);                       // the longest line the guest may send

// metadata from the caller: building the plugin starts nothing
let plugin = guest.plugin(GuestMeta::new("jira").provide("jira"));
let fiber = ctx.plugin_def(&plugin, config)?;

// or metadata from the guest, as ProcessSource reads it
let module = guest.module("plugins/jira")?;
```

| `ProcessGuest` | |
|---|---|
| `new(command)` | 运行 `command` 的访客（`GuestCommand`：程序、`arg`/`args`、`env`、`current_dir`） |
| `spawner(spawner)` | 由谁启动它的进程（见下文）；默认为 `StdSpawner` |
| `timeout(duration)` | 调用者未设置截止时间时，每次导出可用的时长；超过后进程被杀死。默认没有，但此时 `dispose` 限定为 5 秒 |
| `handshake_timeout(duration)` | 访客应答[握手](#process)的时限（默认 10 秒） |
| `frame_limit(bytes)` | 访客可发送的最长一行（默认 16 MiB）；更长的一行会使访客被杀死 |
| `plugin(meta)` | 访客的插件，其 `GuestMeta`（`new(name)`、`.inject(key)`、`.provide(key)`）由调用者给出。每个进程启动时必须声明相同的元数据（相同的名称，以及顺序不限的相同服务），否则其纤程失败 |
| `module(id)` | 访客的模块，其元数据从为此启动的进程中读取 |

### Spawner [#spawner]

`Spawner` 负责启动进程，由应用决定访客如何运行（沙箱、进程组、拥有它的进程管理器）：

```rust
pub trait Spawner: Send + Sync + 'static {
    fn spawn(&self, command: &GuestCommand) -> io::Result<GuestProcess>;
}
```

它得到命令的程序、参数、环境变量和工作目录（`get_program`、`get_args`、`get_envs`、`get_current_dir`，或用 `to_std()` 得到 `std::process::Command`），并返回一个 `GuestProcess`：进程的 stdin 和 stdout，可选的 stderr（`.stderr(…)`，用于[退出报告](#exit)），以及一个 `GuestChild`，即实例在进程结束前一直持有的控制句柄（`id`、`kill`、`try_wait`、`wait`，与 `std::process::Child` 相同）。`GuestProcess::from_child` 接受以管道方式启动 stdio 的 `std::process::Child`。默认的 `StdSpawner` 用 `std::process` 在应用的环境加上命令的变量中运行命令。实例用完进程时（释放时，或访客失败时）会杀死它。

### 退出报告 [#exit]

每个进程访客都有一个 `GuestHandle`，可从 `GuestService::handle()` 或 `GuestStarted` 事件获得：

| `GuestHandle` | |
|---|---|
| `id()` | spawner 报告的进程 id |
| `protocol()` | 访客使用的协议：`1` 或 `2`（`kardia-guest/2`） |
| `exit()` | 进程结束后的 `GuestExit` 报告 |
| `subscribe()` | 报告的 `tokio::sync::watch` 接收端（进程运行期间为 `None`） |
| `exited()` | 以报告完成的 future |
| `stderr_tail()` | 进程迄今写入 stderr 的最后 16 KiB |
| `kill()` | 杀死进程；其报告注明 `killed by the host` |
| `ping(timeout)` | 检查 `kardia-guest/2` 访客是否应答，即使它正在执行调用；以往返时间完成 |

`GuestExit` 包含退出状态 `status`、原因 `cause`（`ExitCause::Exited` 为自行退出，`Killed(reason)` 为错过截止时间、违反协议或 `kill()`，`Disposed` 为被其纤程释放）以及 `stderr_tail`（16 KiB）。stderr 的每一行也会以插件的身份在 `debug` 级别记录。

桥接插件会在访客的纤程上发出两个事件：进程启动后、`apply` 之前发出 `GuestStarted { fiber, handle }`；进程在纤程释放它之前结束时发出 `GuestExited { fiber, exit }`。随后纤程以该报告为错误失败（`Fiber::fail`），撤回它的服务，其使用者会重新等待这些服务。与任何失败的纤程一样，`restart` 会让它保持失败；`fiber.update(config)` 会启动一个新进程。

```rust
use kardia::hmr::GuestExited;

ctx.on(|event: &GuestExited| {
    let tail = String::from_utf8_lossy(&event.exit.stderr_tail);
    eprintln!("{} ended: {}\n{tail}", event.fiber.name(), event.exit);
})?;
```

## 自定义传输 [#transports]

各后端实现了两个公开 trait，宿主可以为自己的传输实现它们：

| | |
|---|---|
| `GuestCode::instantiate(&self, host: GuestHost) -> Result<Box<dyn GuestInstance>>` | 启动一个实例，其宿主调用作用于 `host`（`log`、`provide`、`view`、`invoke`）；在异步工作线程之外调用 |
| `GuestInstance::call(&mut self, export, input, control: &CallControl) -> Result<Vec<u8>>` | 以 UTF-8 JSON 输入调用一个 `Export`（`Meta`、`Apply`、`Call`、`Dispose`），返回访客的输出或错误；应在 `control.deadline()` 时停止，并在 `control.is_cancelled()` 后丢弃结果（`on_cancel` 会唤醒它） |
| `GuestInstance::handle(&self) -> Option<GuestHandle>` | 背后的进程（如有；默认为 `None`） |

`kardia::hmr::guest_module(id, code)` 把一个 `GuestCode` 变为模块代码，元数据从一个新实例中读取；`guest_plugin(code, meta)` 把它变为元数据由调用者给出的插件。`ProcessGuest` 和 `WasmGuest` 是进程后端和 WASM 后端的 `GuestCode`，它们的 `plugin(meta)` 和 `module(id)` 就是这两个函数。实例失败的传输应返回 [`GuestFailure`](#guest-failure)，以便调用者把这种失败与访客自己的错误区分开。

## 用 Rust 编写访客 [#sdk]

与 kardia 的其余部分（GPL-3.0-only）不同，`kardia-guest` 采用 MIT OR Apache-2.0 许可证，因此链接它的访客可以自行选择许可证。

创建一个依赖 `kardia-guest` 的 `cdylib` crate：

```toml
[lib]
crate-type = ["cdylib"]

[dependencies]
kardia-guest = "0.2"
```

实现 `Guest` 并用 `export!` 导出：

```rust
use kardia_guest::{Guest, Host, Level, Map, Meta, Request, Result, Value, json};

struct Counter {
    count: u64,
}

impl Guest for Counter {
    type Config = Value;

    fn meta() -> Meta {
        Meta::plugin("counter").provide("counter")
    }

    fn apply(host: &Host, config: Value, _imports: Map<String, Value>) -> Result<Self> {
        host.provide("counter", &json!({ "config": config }))?;
        host.log(Level::Info, "counting");
        Ok(Counter { count: 0 })
    }

    fn call(&mut self, _: &Host, request: Request) -> Result<Value> {
        match request.method.as_str() {
            "increment" => {
                self.count += 1;
                Ok(json!(self.count))
            }
            method => Err(format!("unknown method {method}").into()),
        }
    }
}

kardia_guest::export!(Counter);
```

### `Guest` trait [#guest-trait]

运行该插件的每个纤程都会得到该类型的一个独立实例。

| 项 | 用途 |
|---|---|
| `type Config: DeserializeOwned` | 插件的配置；按原样解码失败时，`null` 会被当作 `{}` 解码 |
| `fn meta() -> Meta` | 模块依赖什么、导出什么 |
| `fn apply(host, config, imports) -> Result<Self>` | 用配置和模块各依赖的值（按解析后的路径为键）启动一个实例 |
| `fn call(&mut self, host, request) -> Result<Value>` | 应答对该实例所提供服务的调用；默认以 `<key> has no method <method>` 失败 |
| `fn dispose(self, host)` | 纤程被释放时、实例被丢弃之前运行；默认什么也不做 |

`Meta` 描述模块：

| `Meta` | |
|---|---|
| `Meta::plugin(name)` | 导出名为 `name` 的插件的模块 |
| `Meta::value(value)` | 导出一个值的模块，依赖它的模块会把该值作为导入收到 |
| `.dep(path)` | 一个依赖：相对于本模块的模块路径 |
| `.inject(key)` | 插件读取的服务；插件在该服务可用时启动 |
| `.provide(key)` | 插件提供的服务 |

`Request` 是 `{ key, method, args }`。`Error` 是报告给宿主的错误消息（`Error::msg(..)`、`error.message()`）；任何可显示的错误都可以用 `?` 转换为它。

### `Host` [#host]

| `Host` 方法 | 作用 |
|---|---|
| `log(level, text)` | 以插件的身份记录日志（`Level::Error` … `Level::Debug`） |
| `provide(key, &value)` | 提供服务 `key`，其 JSON 视图为 `value`；对它的调用会到达 `Guest::call`。纤程被释放时撤回。该键必须用 `Meta::provide` 声明：宿主拒绝其他任何键，且不提供任何东西。 |
| `view(key)` | 用 `Meta::inject` 声明的服务（或由本插件及其祖先提供的服务）的 JSON 视图，按插件所声明 `inject` 的受检访问规则读取 |
| `invoke(key, method, &args)` | 调用另一个访客提供的服务 |
| `cancelled()` | 宿主是否已取消正在运行的导出，以便耗时的调用提前结束；只有以 `kardia-guest/2` 服务的进程访客会收到通知 |

在 Rust 宿主代码中，通过 `GuestService` 调用访客的服务（见[上文](#guest-service)）。

### 构建 [#build]

同一份源码既可构建为 WebAssembly 访客，也可构建为动态库访客。`export!` 在 `wasm32` 上生成 WASM 导出，在其他平台上生成 C 符号：

```sh
rustup target add wasm32-unknown-unknown                # once
cargo build --release --target wasm32-unknown-unknown   # target/wasm32-unknown-unknown/release/<crate>.wasm
cargo build --release                                   # target/release/lib<crate>.so (or .dylib / .dll)
```

对于**进程访客**，在 crate 中加入一个二进制，其 `main` 负责服务访客。请使用 `crate-type = ["cdylib", "rlib"]`，以便二进制能使用这个库：

```toml
[lib]
crate-type = ["cdylib", "rlib"]

[[bin]]
name = "my-guest-process"
path = "src/main.rs"
```

```rust
fn main() {
    kardia_guest::serve::<my_guest::Counter>();
}
```

```sh
cargo build --release --bin my-guest-process            # target/release/my-guest-process
```

`serve` 应答宿主通过 stdin 以 JSON 行发来的导出调用，直到宿主释放该实例或 stdin 关闭。宿主提供 `kardia-guest/2` 时它使用该协议，否则使用协议版本 1：前一种情况下由一个线程读取 stdin，因此导出运行期间也能应答 ping，`Host::cancelled` 也能看到取消。stdout 用于承载协议，因此进程访客不得向它打印；应通过 `Host::log` 或 stderr 记录日志。

### 带依赖的模块 [#deps]

模块可以依赖其他模块，也可以导出一个值而不是插件：

```rust
// shared.rs, built as shared.wasm: exports a value
impl Guest for Shared {
    type Config = Value;
    fn meta() -> Meta {
        Meta::value(json!({ "greeting": "hello" }))
    }
    fn apply(_: &Host, _: Value, _: Map<String, Value>) -> Result<Self> {
        Ok(Shared)
    }
}

// greeter.rs, built as greeter.wasm next to it
impl Guest for Greeter {
    type Config = Value;
    fn meta() -> Meta {
        Meta::plugin("greeter").dep("./shared.wasm")
    }
    fn apply(host: &Host, _: Value, imports: Map<String, Value>) -> Result<Self> {
        let shared = imports.values().next().cloned().unwrap_or_default();  // keyed by resolved path
        host.log(Level::Info, shared["greeting"].as_str().unwrap_or("hi"));
        Ok(Greeter)
    }
}
```

`shared.wasm` 变化时，热重载也会重载 `greeter`，因为它导入了发生变化的模块（见 [reconcile 事务](/docs/guide-hot-reload#reconcile)）。既不导出插件也不导出值的模块什么也不导出。

## 失败行为 [#failures]

访客中的错误或 panic 只会让该插件或该次调用失败：

| 后端 | 访客 panic 时 | 访客消失时 |
|---|---|---|
| dylib | SDK 捕获它并作为错误返回：`the guest panicked: <message>` | 崩溃会使宿主崩溃 |
| process | SDK 捕获它并作为错误返回：`the guest panicked: <message>` | 已退出的进程会以其[退出报告](#exit)使插件的纤程失败，其调用以 `the guest process exited` 失败；破坏协议（`invalid message from guest: …`）、发送超过帧上限的一行或超过调用截止时间（`the guest did not answer in time`）的进程会被杀死，结果相同 |
| WebAssembly | 访客中止（abort），宿主把中止报告为一次失败的调用 | 设置上限时，燃料或时间耗尽的导出触发陷阱，该实例之后的调用失败 |

- `apply` 返回的错误会使插件的纤程失败（`Failed`）；`call` 返回的错误只让该次调用失败，实例继续运行。
- `dispose` 中的 panic 会被吞下，因为宿主没有可报告的对象。
- 已释放或已失败实例的进程绝不会继续运行；`dispose` 之后宿主会杀死它，`dispose` 本身也受访客超时的限制（未设置时为 5 秒）。宿主消失时，进程访客会退出。
- 读取模块元数据（`meta`）期间没有插件上下文：宿主调用以 `host calls are unavailable while reading module metadata` 失败。
- 访客只能提供其元数据在 `provide` 中声明的服务：提供其他服务会以 `cannot provide "<key>": the plugin does not declare it in provide` 失败，且不提供任何东西，因此没有消费者能看到该服务，哪怕是短暂地。

### 带类型的失败 [#guest-failure]

当访客实例本身失败（而不是访客报告一个错误）时，调用以 `kardia::hmr::GuestFailure` 失败：它的 `kind`（一个 `GuestFailureKind`）说明失败的方式，其文本就是错误消息，与以前相同。`GuestFailure::of(&error)` 从 `kardia_core::Error` 中找出它，`error.downcast_ref::<GuestFailure>()` 也可以。访客自己报告的错误（失败状态码，或 SDK 返回的错误）、缺少的导出、已释放的实例，以及因等待另一个调用结束而超时的调用，都不是 `GuestFailure`；实例继续运行。

| `GuestFailureKind` | 何时 |
|---|---|
| `Trap` | WASM 访客触发陷阱（`wasm trap: …`），或在它运行时某个宿主函数失败 |
| `OutOfFuel` | WASM 导出耗尽了燃料；该实例之后的调用以同样的方式失败（`the guest was stopped: …`） |
| `Timeout` | WASM 导出在截止时间被中断（该实例之后的调用以同样的方式失败），或进程访客在截止时间被杀死（`the guest did not answer in time`） |
| `OutOfMemory` | WASM 访客的内存增长被拒绝（`forcing trap when growing memory …`） |
| `Exited` | 访客进程自行结束（`the guest process exited`；纤程的失败则是其[退出报告](#exit)） |
| `Killed` | 访客进程被杀死：它破坏了协议、发送了超过帧上限的一行、为它服务的线程发生了 panic，或宿主杀死了它（纤程以其退出报告失败） |
| `Panicked` | 某次访客调用在宿主一侧发生了 panic，或 WASM 的 epoch 线程发生了 panic（此后设有时间上限的调用都会失败） |

kardia-hmr 启动的线程（进程访客的 `guest-stdin`、`guest-stdout`、`guest-stderr` 线程，以及设有时间上限的引擎的 `wasm-epoch` 线程）会捕获自己的 panic：此时进程访客会被杀死，其退出报告和失败调用的原因为 `the <thread> thread panicked: <message>`。如果 panic 钩子会在遇到不确定是否被捕获的 panic 时中止进程，可以询问 `kardia::hmr::is_panic_contained()`，它在这些线程上为 true。

## 访客 ABI [#abi]

其他语言编写的访客需实现这一接口，它也记录在 `kardia-hmr` 的 crate 文档中（`cargo doc -p kardia-hmr --open`）。

数据以字节缓冲区中的 UTF-8 JSON 形式跨越边界。宿主为每个实例保留一条**消息**：先是被调用导出的输入，之后是上一次宿主调用的结果。访客按给定的长度分配内存后，用 `read` 把消息复制到自己的内存中。

**导出**（状态 `0` 表示成功；失败时访客用 `write` 写出错误）：

| WASM | dylib | |
|---|---|---|
| `memory` | `cordis_new() -> state` | 内存 / 每个实例的访客状态 |
| `cordis_meta() -> i32` | `cordis_meta(state, host) -> i32` | `write` 出 `{ deps?, plugin?: { name?, inject?, provide? }, value? }` |
| `cordis_apply(len) -> i32` | `cordis_apply(state, host, len) -> i32` | 消息：`{ config, imports }` |
| `cordis_call(len) -> i32` | `cordis_call(state, host, len) -> i32` | 消息：`{ key, method, args }`；`write` 出结果 |
| `cordis_dispose()`（可选） | `cordis_dispose(state, host)` | 最后一次调用；dylib 在此释放 `state` |

`deps` 是相对于本模块的模块路径；`imports` 把每个导出了 `value` 的依赖映射到该值。既不导出插件也不导出值的模块什么也不导出。

**名称。** 每个导出和 dylib 符号也可以用 `kardia_*` 代替 `cordis_*` 命名（`kardia_meta`、`kardia_new` 等）。宿主对每一项都先查找 `kardia_*`，找不到时再查找 `cordis_*`，因此访客可以只导出其中一套、混用两套，或两套都导出：两者都存在时，宿主调用 `kardia_*` 的那个。WASM 宿主函数同时在 `kardia` 和 `cordis` 两个导入模块下提供，一个模块可以从其中任意一个或两个导入。kardia-hmr 0.2.0 及更早的宿主只认识 `cordis_*` 和 `cordis`，因此 `kardia-guest`（以及 pykardia 的导出工具）会以两套名称导出每一项，并从 `cordis` 导入宿主函数：这样构建的访客在新旧宿主上都能加载。

**宿主函数**（WASM 从模块 `cordis` 或 `kardia` 导入；dylib 则是 `host` 结构体 `{ host, read, write, log, provide, view, invoke }` 中的函数指针，每个都以 `host.host` 作为第一个参数）。指针是访客地址，长度是字节数：

- `read(ptr)` 把消息复制到 `ptr`。
- `write(ptr, len)` 设置当前导出的结果。
- `log(level, ptr, len)` 以插件的身份记录日志（`0` error … `3` debug）。
- `provide(key, key_len, value, value_len) -> i32` 把服务 `key` 作为 `GuestService` 提供，其 JSON 视图为 `value`。插件元数据未在 `provide` 中声明的键会以错误被拒绝，且不提供任何东西。
- `view(key, key_len) -> i32` 按插件所声明 `inject` 的受检访问规则，读取某个服务的 JSON 视图。
- `invoke(key, key_len, method, method_len, args, args_len) -> i32` 调用一个 `GuestService`。

返回 `i32` 的宿主函数会把消息设为其结果并返回其长度；或把消息设为错误消息并返回 `-1 - len`。

**模块的生命周期。** 加载模块时会实例化它一次以读取元数据（先 `meta`，再 `dispose`）；`deps` 中的依赖先加载。之后运行该插件的每个纤程都会得到一个新实例：以 `{ config, imports }` 调用 `apply`，任意次 `call`，以及纤程被释放时的 `dispose`，之后实例被丢弃。状态非零且没有写出任何内容时，以 `guest failed with status <n>` 失败。

### 进程传输 [#process]

进程访客通过 stdin 和 stdout 每行交换一个 JSON 对象（stdout 专用于此；访客通过 `log` 或 stderr 记录日志）。协议有两个版本：版本 1，以及增加了握手、请求 id、取消和 ping 的 `kardia-guest/2`。

**握手。** 宿主的第一行以导出的形式提供版本 2：`{"export":"hello","input":{"protocol":"kardia-guest/2"}}`。版本 2 的访客应答 `{"ready":"kardia-guest/2"}`。版本 1 的访客应答 `{"done":1}`（它对任何不认识的导出都这样应答），宿主随后按版本 1 为它服务。因此两种访客都能立即启动，版本 2 的访客在从不提供它的宿主上也能运行。在握手时限内没有应答的访客会被杀死。

**版本 1：**

| 方向 | 消息 | 含义 |
|---|---|---|
| 宿主 → 访客 | `{ export, input }` | 一次导出：`export` 为 `meta`、`apply`、`call`、`dispose` 之一；`input` 是消息（为空时为 `null`） |
| 访客 → 宿主 | `{ call: "log", level, text }` | 记录日志；无应答 |
| 访客 → 宿主 | `{ call: "provide", key, value }` | 以 `{ result }` 或 `{ error }` 应答（未声明的 `key` 是错误） |
| 访客 → 宿主 | `{ call: "view", key }` | 以 `{ result }` 或 `{ error }` 应答 |
| 访客 → 宿主 | `{ call: "invoke", key, method, args }` | 以 `{ result }` 或 `{ error }` 应答 |
| 访客 → 宿主 | `{ output }` | 设置导出的结果文本 |
| 访客 → 宿主 | `{ done: status }` | 结束这次导出 |

**`kardia-guest/2`** 发送相同的消息，但每条都带有 `id`：每次导出带一个新的 `id`，与它有关的每条消息都带同一个 `id`（`{"id":3,"call":"view","key":"db"}`、`{"id":3,"result":…}`、`{"id":3,"output":…}`、`{"id":3,"done":0}`）。宿主一次只调用一个导出。另有两条消息不需要正在运行的导出：

| 方向 | 消息 | 含义 |
|---|---|---|
| 宿主 → 访客 | `{ cancel: id }` | 调用者不再需要导出 `id`：访客可以提前结束；宿主丢弃其结果，并以错误应答它之后的宿主调用 |
| 宿主 → 访客 | `{ ping: n }` | 以 `{ pong: n }` 应答，即使有导出正在运行 |

`dispose` 之后进程会被杀死；stdin 关闭时访客退出。

例如，上面的 `Counter` 访客在没有配置的情况下被应用，然后被调用一次：

```text
→ {"export":"apply","input":{"config":null,"imports":{}}}
← {"call":"provide","key":"counter","value":{"config":null}}
→ {"result":null}
← {"call":"log","level":2,"text":"counting"}
← {"done":0}
→ {"export":"call","input":{"key":"counter","method":"increment","args":null}}
← {"output":"1"}
← {"done":0}
```

在 `kardia-guest/2` 下相同的过程：

```text
→ {"export":"hello","input":{"protocol":"kardia-guest/2"}}
← {"ready":"kardia-guest/2"}
→ {"id":1,"export":"apply","input":{"config":null,"imports":{}}}
← {"id":1,"call":"provide","key":"counter","value":{"config":null}}
→ {"id":1,"result":null}
← {"id":1,"call":"log","level":2,"text":"counting"}
← {"id":1,"done":0}
→ {"id":2,"export":"call","input":{"key":"counter","method":"increment","args":null}}
← {"id":2,"output":"1"}
← {"id":2,"done":0}
```

## 手写访客：`hello.wat` [#hello]

`examples/plugins/hello.wat` 是用 WebAssembly 文本手写的访客。它从 `cordis` 模块导入 `write` 和 `log`，并导出 `memory` 和三个函数：

```text
;; A guest plugin in WebAssembly text (see the guest ABI in the kardia-hmr
;; docs). Edit the greeting while the app runs: hmr reloads this module in
;; place, disposing the old instance first.
(module
  (import "cordis" "write" (func $write (param i32 i32)))
  (import "cordis" "log" (func $log (param i32 i32 i32)))
  (memory (export "memory") 1)

  (data (i32.const 0) "{\"plugin\":{\"name\":\"hello\"}}\00")
  (data (i32.const 128) "goodbye from wasm\00")
  (data (i32.const 256) "hello from wasm\00")

  ;; the length of the NUL-terminated string at $ptr
  (func $len (param $ptr i32) (result i32)
    (local $end i32)
    (local.set $end (local.get $ptr))
    (block $done
      (loop $next
        (br_if $done (i32.eqz (i32.load8_u (local.get $end))))
        (local.set $end (i32.add (local.get $end) (i32.const 1)))
        (br $next)))
    (i32.sub (local.get $end) (local.get $ptr)))

  (func $info (param $ptr i32)
    (call $log (i32.const 2) (local.get $ptr) (call $len (local.get $ptr))))

  (func (export "cordis_meta") (result i32)
    (call $write (i32.const 0) (call $len (i32.const 0)))
    (i32.const 0))

  (func (export "cordis_apply") (param i32) (result i32)
    (call $info (i32.const 256))
    (i32.const 0))

  (func (export "cordis_dispose")
    (call $info (i32.const 128))))
```

- `cordis_meta` 写出 `{"plugin":{"name":"hello"}}`：一个名为 `hello` 的插件，没有依赖、注入或提供。它返回 `0`。
- `cordis_apply` 忽略其输入（从不 `read` 消息），并以级别 `2`（info）记录 `hello from wasm`。
- `cordis_dispose` 记录 `goodbye from wasm`。
- 没有 `cordis_call`，因为该插件不提供任何服务。

用 `cargo run -p kardia -- examples/kardia.yml` 运行它并编辑问候语：`hmr` 会原地重载该模块，于是旧实例先记录道别，新实例再记录你的问候语。
