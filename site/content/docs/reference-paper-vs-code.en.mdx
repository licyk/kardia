This page compares the theory (the paper's model and its pseudo-code, §3–5; see [Concepts](/docs/concepts)) with the implementation (the TypeScript code at `cordis/`). It is the bridge used by the Rust design: where the two differ, the [Development](/docs/development) pages state which one kardia follows and why.

## Deviations and refinements [#deviations]

### Target representation [#target]

- **Paper:** `fiber.target` is a hash of `target(γ, n)` (key → provider uid tuple), ⊥ when unsatisfied.
- **Code:** `_runner.epoch` = `"<revision>:<uid>:<uid>…"` or `'__INACTIVE__'`. The **revision** counter folds configuration revisions into the target: `restart()`, `update()` and `registry.replace()` bump it, forcing an unload→reload chain without retiring the fiber. This realizes the §4.4 *Configuration* revision more cheaply than retire → remove → reinsert at the same name.

See [Target computation](/docs/reference-fibers#target).

### Retirement and removal [#retirement]

- **Paper:** O-Retire (set τ) and O-Remove (drop the entry) are separate rules; a retired entry may linger (vestigial).
- **Code:** the instantiation effect's inverse sets `uid = null` (removed from the runtime immediately), forces the target to ⊥, then awaits the transition chain; the final state is `DISPOSED`. There is no persistent registry of retired entries. Re-enabling an entry creates a **fresh fiber** (as the paper prescribes).

See [Instantiation](/docs/reference-fibers#instantiation).

### Guard implementation [#guard]

- **Paper (Algorithm 5):** `unload` awaits the `notify(...)`'d dependents' `await()`.
- **Code:** explicit reverse references `Impl.dependents: Set<Fiber>`, populated at commit time and removed at the end of the dependent's unload, plus wake-up resolvers (`impl.release`, `fiber._release`). Two guards exist: the **fiber-level** guard (no disposer of the provider runs until *all* its provisions are free) and the **binding-level** guard inside `provide`'s inverse. This gives the paper's per-binding semantics (`relied_n`) while letting a provider withdraw one binding without waiting for another.

See [The two guards](/docs/reference-fibers#guards).

### Accumulator execution order [#accumulator]

- **Paper:** the accumulator is a LIFO composite; Algorithm 5 runs `fiber.dispose()` once.
- **Code:** fiber-level disposers are *initiated* in reverse order but run **concurrently** (`Promise.all`), each after one microtask; errors are logged and do not stop the others. Sequential LIFO holds only *inside* one `ctx.effect`. The paper acknowledges the concurrency (§5.1.3) and it is justified by Theorem 43 (independent inverses commute), but it means ordering-sensitive teardown must be grouped into one effect.

See [Fiber-level accumulator](/docs/reference-effects#accumulator).

### Iteration boundaries [#iteration-boundaries]

- **Paper:** the guard is checked before each iteration; L-Divert may abort or land.
- **Code:** only **async** iterators are interruptible; sync iterators and plain functions run to completion (they cannot be interrupted in a single-threaded host anyway). Async iterators take the *landing* alternative (an inertial host) and are closed with `iter.return()` so `finally` blocks run. `_reload` also yields one microtask before executing, so superseded loads never start.

### Notification [#notification]

- **Paper:** `notify` iterates all fibers and calls `refresh`.
- **Code:** it iterates all runtimes' fibers, filters by declared key and **realm symbol** (or a custom filter during realm moves), recomputes only the affected keys (`_checkImpl`), then calls `_refresh`. It also emits `internal/service`. Notifications for a fiber's provisions are issued from `_updateState` only on transitions into or out of `ACTIVE`.

See [`notify`](/docs/reference-context#notify).

### Availability predicate [#availability]

The code adds `Impl.check` (from `Service[symbols.check]`): a provider may report itself unavailable even while `ACTIVE` (used by `loader` for `{ await: true }`). This extends the satisfaction predicate `σ ⊧ d` with a per-provider condition.

### Access resolution [#access]

`locate` additionally (a) lets a fiber read its **own** provisions without declaring them and (b) stops inheritance at an **isolation boundary**. The root fiber (no runtime) gets *unchecked* access (`reflect.get(prop, false)`), because root code cannot declare `inject`. See [`locate`](/docs/reference-context#locate).

### Caller attribution (not in the paper) [#caller-attribution]

The tracker/shadow proxy mechanism ([Services and traceability](/docs/reference-services)) attributes effects created inside service methods to the **calling** fiber and resolves the service's own dependencies from its **def site**. The paper's confinement (Def. 55) implicitly assumes this; without it, service-mediated effects would belong to the provider and break temporal composability for consumers.

### Loader specifics not in the paper [#loader-specifics]

See [Loader](/docs/reference-loader).

- Two fibers per entry with `inject` (an outer dependency holder + the inner plugin).
- Expressions (`!!js`) evaluated in specific contexts; a cached `disabled` verdict.
- Self-dispose detection → persisted `disabled: true`; self-update → persisted config (`internal/commit`).
- The `loader { await: true }` barrier.
- Realm migration without restarting the provider; blocked moves tracked via `Impl.isolate`.

### HMR [#hmr]

See [HMR: Paper vs. code](/docs/reference-hmr#paper-vs-code): registry-level in-place replacement (`registry.replace` + `_replace` + revision bump) instead of dispose + `ctx.use`; union-find commit units instead of all-or-nothing; no rollback after the point of no return.

### Things the paper assumes that the code does not check [#unchecked]

| Assumption | Status in the code |
|---|---|
| Effect witnesses (the inverse really reverts) | unchecked, an author obligation (stated in the paper) |
| Coeffect commutativity | unchecked, a provider obligation (stated in the paper) |
| Acyclicity of ≺ | **not detected**: a dependency cycle leaves fibers PENDING silently; the paper (§6.5) says a runtime *can* report it at load time, but Cordis does not |
| Totality on provision (Def. 76) | not enforced; `provide` metadata on plugins is declarative only |
| Confinement (Def. 55) | enforced only for coeffect *access* through the proxy; arbitrary JS can still reach globals |

| Location | Observation |

| `create/src/index.ts` | `--mirror` flag parsed but unused. |

## Implications for the Rust port [#rust]

<Steps>
<Step>
Follow the **code's** state machine (epoch with revision, inertia, two-level guard, `FAILED`, `DISPOSED`), because it is tested and handles configuration revisions; keep the paper's names in the docs.
</Step>
<Step>
Follow the **paper** where the code is constrained by JS: make iteration boundaries explicit for all multi-step effects; detect dependency cycles at insertion time (cheap, since declarations are static).
</Step>
<Step>
Replace Proxy-based caller attribution with explicit typed handles.
</Step>
<Step>
Follow the **code's** HMR design (unit-wise commit, in-place replacement) over Algorithm 10.
</Step>
<Step>
Fix the realm-GC early `return` in the port.
</Step>
</Steps>

How kardia carries these out is described in [Lifecycle](/docs/development-lifecycle), [API design](/docs/development-design), [Loader, include and HMR](/docs/development-loader) and, with every deviation listed, [Status](/docs/development-status).
