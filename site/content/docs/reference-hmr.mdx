## 集成 [#integration]

`class Hmr extends Service`，服务名 `hmr`。配置：

| 键 | 默认值 | 含义 |
|---|---|---|
| `base?` | `ctx.baseUrl` | 基础目录 |
| `watch.enabled` | `false` | 文件变化时重新加载 |
| `watch.files` | `['.', '!**/node_modules', '!**/.*']` | glob 过滤器 |
| `watch.debounce` | 100 ms | 重新加载前的防抖时间 |

- 它需要 Node 的内部 ESM 加载器（`loader-utils` → `ModuleLoader.fromInternal()`，需要 `--expose-internals` 或 `node-addon-require-builtin` 原生扩展）；否则构造函数抛出异常（纤程（fiber）FAILED，没有服务）。
- 监听是一个可选的嵌套插件 `ctx.inject(['fs'], ...)`，只在存在 `fs` 服务时活跃。
- `[Service.init]` 记录**宿主（host）模块**：`process.argv[1]` 的导入闭包（主程序、core、loader……），它们只能通过重启进程来改变。
- 没有任何加载器特有的代码：加载器通过同一个内部 ESM 加载器导入插件，因此它们的模块就在 hmr 检查的缓存中。hmr 在**注册表**（registry）层面替换插件，加载器的条目（entry）保留其纤程。

## 模块图 [#module-graph]

hmr **不维护自己的图**。它每次都从 Node 的 ESM `loadCache`（`ModuleJob.linked`）与 CJS 的 `require.cache` 读取实时的图（`_edges`、`closure`）。内置模块（`node:`）被跳过；原生扩展（native addon，`.node`）无法被重新加载。

## `reconcile(callback)`：一个事务 [#reconcile]

`index.ts:309-699`。事务在一个 promise 队列上串行执行；从事务内部发起的重入调用（来自回调，或来自第 3 阶段中某个插件的 `apply`）会借助 `AsyncLocalStorage` 被拒绝。

<Steps>
<Step>
**根（Roots）**：`await callback()` → 绝对路径（经校验）。
</Step>
<Step>
**清扫（Sweep）**：按类型槽位，从缓存中逐出*失败的* ModuleJob（Node 会保留它们，并在每次导入时重新抛出）。
</Step>
<Step>
**匹配（Match）**：路径以某个根为祖先的已加载模块（按完整路径段匹配）。宿主模块与原生扩展 → `skippedHostModules`（仅报告）。
</Step>
<Step>
**分析（Analyze）**：反向边（不含来自宿主模块的边）。`accepted` = 变化的模块加上所有传递地导入它们的模块；`declined` = 宿主 ∪ 其余。*（论文的算法 8 是在正向导入上求不动点，环默认为 declined；代码则是更简单的反向可达工作表。）*
</Step>
<Step>
**发现（Discover）**：对 accepted 模块解包其导出，保留其中已注册的插件；**按 runtime 分组**（多个模块可以导出同一个插件）。
</Step>
<Step>
**过时插件（Stale plugins）**：对每个 runtime，取其导出者经由 accepted 模块的闭包。要重新导入的模块是**最外层的导出者**（保留入口模块的 `inject`/`Config` 元数据）。
</Step>
<Step>
**备份并逐出**每个要逐出的 URL（整个多槽位 ESM 条目 + CJS 模块）。
</Step>
<Step>
**第 1 阶段，导入**，对每个过时插件依次执行：重新导入，并检查其导出是一个有效插件（`registry.resolve`）。*所有可能失败的校验都发生在这里，此时只有模块缓存被修改过*，因此后续阶段无需回滚。在所有插件都导入完成之前，不恢复任何缓存条目。
</Step>
<Step>
**用并查集划分单元**：若两次尝试的**旧 ∪ 新**闭包共享某个被逐出的模块，它们就并入同一个单元（共享同一个变化依赖的两个插件，不能最终持有该依赖的不同实例）。
</Step>
<Step>
**中止/提交**：存在任何导入失败的单元被中止，其模块被恢复。孤立的被逐出模块随与之重叠的中止单元一起恢复（除非它们能到达某个已提交单元）。与已恢复模块链接的第 1 阶段加载模块会被逐出。
</Step>
<Step>
**第 2 阶段，替换（同步）**：对每个已提交的尝试执行 `ctx.registry.replace(oldPlugin, newPlugin)`。`replace` 把旧插件键作为新插件的别名（此后 `ctx.plugin(old)` 实例化新代码），并在每个纤程上调用 `fiber._replace(newRuntime, newInject)`：重新检查依赖、清除错误、递增修订号 ⇒ **同一个纤程对象原地卸载并重新加载**（身份、父级、配置与加载器条目均被保留）。
</Step>
<Step>
**第 3 阶段，稳定（并发）**：`await Promise.all(fibers.map(f => f.await().catch(noop)))`。**没有回滚**：新 `apply` 抛出的插件保持 FAILED（与冷启动时一样），并在下一次变化时重试。
</Step>
</Steps>

结果为 `{ settledFibers, importFailures: { urls, error }[], skippedHostModules }`。

### 状态保留 [#state-preservation]

| 保留 | 丢失 |
|---|---|
| 纤程对象与 uid、父级、配置、加载器条目、*其他*纤程的服务 | 旧实例的全部效应（由正常的卸载路径释放，它会先等待依赖方，因此新实例永远不会与旧实例重叠），以及被重新导入模块的模块级状态 |

无关的插件不受影响。不同的纤程并发地重新加载（一个慢的排空不会拖慢一个快的插件）。

## 监听模式 [#watch]

`index.ts:135-186`。`ctx.fs.watch(baseDir, { filter }).on('change', f => …)` → 防抖 → 串行的 `flush`，协调 `retained ∪ stashed`。

- 宿主模块的变化会给出警告。
- 失败单元的文件会被**保留**，并与下一次变化一起重试（当一个坏文件与其依赖中只有一个被修复时，二者会一起重试）。
- 只有 `change` 事件；新文件只有在某个变化的导入者导入它时才有意义。

## 论文与代码对照 [#paper-vs-code]

| 方面 | 论文（算法 8–10） | 代码 |
|---|---|---|
| 分类 | 正向不动点；环默认为 declined | 从变化模块出发的反向可达；宿主模块 declined |
| 过时检测 | 按*条目*（`entry.url`） | 按*插件 runtime*（任何由 accepted 模块导出的已注册插件）；与加载器无关 |
| 替换 | `entry.fiber.dispose(); entry.fiber ← ctx.use(import(url), config)` | `registry.replace` → 同一个纤程对象原地重新加载 |
| 失败处理 | 恢复缓存并从备份重建*每个*过时条目，重新抛出 | 在第 1 阶段校验；失败的**单元**（并查集）被中止并恢复，其他单元提交；新 `apply` 的失败保持 FAILED（不回滚） |
| 原子性 | 全有或全无 | 按依赖连通的单元 |
| 重入 | 未讨论 | 串行队列 + AsyncLocalStorage 拒绝 |

代码的设计可以说更强：提交/中止按单元进行，而且“不可回头点”被放在唯一一个可以干净还原的可失败步骤之后。

## Node 特有的部分 [#node-specific]

[模块图](#module-graph)中的全部内容，以及事务的第 2、7–8、10 步，都依赖于 Node 的模块缓存与内部机制。而*算法*本身（匹配 → 接受 → 按 runtime 分组 → 第 1 阶段校验 → 并查集单元 → 原地替换 → 稳定）只要存在一个由宿主拥有的模块注册表即可移植。kardia 的设计见[加载器、include 与 HMR](/docs/development-loader)。
