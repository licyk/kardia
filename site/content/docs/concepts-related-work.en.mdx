This page summarises §6–8 of the paper ([arXiv:2608.25512](https://arxiv.org/abs/2608.25512)): theory and design guidance. The paper's notes that bear on a Rust port are marked **[Rust]** in the source summary; here each is followed by an "In kardia" callout saying how kardia realises it.

## System boundary (§6.1)

The boundary divides the environment into locations **inside** (the system can modify them exclusively *and* restore them, so they are tracked and revertible) and **outside** (either ability fails, so the operation acts as `id_Γ` and is untracked).

- **Coeffects move the boundary** by reifying an external location behind operations that each have an inverse. The boundary is drawn *per location*, not per medium (a private scratch file is inside; a shared path is outside).
- **Acquisition vs. emission.** Reaching outside happens in two stages: *acquisition* installs a record inside the boundary (`open` → descriptor, `malloc` → block, `fork` → child), which is revertible; *emission* pushes data through that channel (`write`, `send`) and crosses outside, which is not revertible.
- **Withholding and compensation.** Recovering an emission requires either withholding it until the producing state is certain (the output-commit problem) or compensation (delete the created file, refund the charge) up to an application-supplied, coarser equivalence. Compensations compose LIFO like inverses, but the commutation metatheory ([Metatheory](/docs/concepts-metatheory)) must be re-established against the coarser relation.

## Service multiplexing (§6.2)

Coeffects echo OSGi services: providers publish under an interface, and consumers bind. Multiple implementations can be realised as:

1. **Exclusive binding**: at most one is bound at a time; switching unloads one provider and loads another, perturbing every consumer.
2. **Service broker**: a central service is injected by both the backing providers and the consumers; providers *register with the broker* through revertible effects; consumers see no change when a backing provider changes.

The broker enables **load balancing** (policy-driven dispatch; scale by loading and unloading providers), **rolling updates** (load the new provider, shift traffic, unload the old one once drained: quiescence/tranquility), and **cross-process invocation** (each process hosts its own context; RPC preserves the interface; it must be designed against an *asynchronous* contract).

**[Rust]** The broker pattern is the recommended way to get many providers per key within the single-provider calculus.

<Callout type="info">
**In kardia:** one key has one provider per realm (a second `ctx.provide` fails with `KardiaError::AlreadyProvided`). A broker is an ordinary service whose registry is an `IdTable`; a backing provider registers with it through an effect created on its own fiber (`svc.caller().effect(..)`), so the registration is withdrawn when that provider unloads. kardia has no separate broker service for guests: each guest fiber's `GuestService` is its own RPC endpoint, and its calls are synchronous rather than the asynchronous contract above, so a hung guest blocks its caller. See [Services](/docs/guide-services) and [Guest plugins](/docs/guide-guests).
</Callout>

## Access control and sandboxing (§6.3)

- **Capability-based access control.** Proxy-mediated access only allows declared dependencies (an undeclared access is an error). `inject` acts as a capability request, the context proxy as a capability mediator. Because declarations are static, the orchestrator can review them at load time.
- **Fine-grained policy through interception**: for example, a filesystem dependency carrying metadata about readable and writable paths, checked by the provider. It is adjustable from the context without modifying the provider; it affects how a dependency is used, not whether it is satisfied, so it can change at runtime without a reload.
- **Sandboxing** untrusted code needs an execution boundary beyond the language (SFI, a separate runtime, a sandboxed process, a container); the untrusted component reaches host dependencies through a *bridge*, itself an ordinary fiber whose capabilities can be attenuated.

## Language independence and selection (§6.4) [Rust]

**Temporal requirements:** closures (an inverse is a captured value), plus a way to introduce and retract a component's code at runtime:

- managed runtimes: a programmatic module registry (Node `require.cache`; ESM has no public eviction API);
- **native code: explicit dynamic linking and unlinking** (`dlopen`/`dlclose`, `LoadLibrary`/`FreeLibrary`);
- **WebAssembly**: an instance is released when a native embedder (for example **Wasmtime**) drops it.

In all cases loading is an effect whose inverses undo the registrations the module introduced.

<Callout type="info">
**In kardia:** `kardia-hmr` loads guest modules through three backends, each running a guest plugin through a bridge plugin that instantiates the guest once per fiber and drops the instance when the fiber is disposed. `WasmSource` runs core WebAssembly modules on Wasmtime (sandboxed, one store per fiber). `DylibSource` loads dynamic libraries but never unloads them (no `dlclose`): unloading Rust code is unsound once it has registered thread-local destructors or handed out `'static` references, so each version is loaded from a fresh copy of the file. `ProcessSource` runs one child process per fiber and kills it after `dispose`. See [Guest plugins](/docs/guide-guests) and [Hot reload](/docs/guide-hot-reload).
</Callout>

**Spatial requirements:** a dependency-injection mechanism at two levels:

- **type level**: a well-typed dependency access; the context type must record each key's coeffect. *Typeclasses (Haskell) and **traits (Rust)** let a provider extend the context type from its own module through an instance/`impl`*; TypeScript uses module augmentation.
- **runtime level**: access must be dynamically mediated (a JavaScript `Proxy`, Python descriptors, or reflection at the cost of type safety).
- **Metaprogramming** supplies both together: *compile-time metaprogramming (for example **Rust procedural macros**, Scala macros, Zig comptime) emits, for each dependency, a typed declaration together with an accessor, dispensing with a general-purpose interception primitive.*

<Callout type="info">
**In kardia:** the `Service` trait binds a type to its key (`#[derive(Service)]`), and a service crate extends what a consumer can do with an extension trait on `Svc<S>` (for example `TimerExt` for `Svc<Timer>`), which coherence allows because the trait is local. Access is mediated at runtime by `ctx.get::<S>()` against the committed view, without a proxy. The `#[plugin]` macro supplies the compile-time half: a plugin function taking `Injected<(A, B)>` declares `A` and `B`, and accessing anything else through it does not compile. See [Plugins](/docs/guide-plugins), [Services](/docs/guide-services) and [API design](/docs/development-design).
</Callout>

## Mutual dependencies and component granularity (§6.5)

A dependency cycle leaves the involved components **permanently inactive**. Unlike a concurrency deadlock it is *predictable from the declarations*, so a runtime can report it at load time. Most cycles decompose: for example, server ↔ access-controller becomes `server-core`, `access-control-core`, `request-mediation` (depending on both cores) and `policy-management` (depending on both). The cost is a potentially quadratic number of integration components, mitigated by package bundling, convention-based wiring and scaffolding.

<Callout type="info">
**In kardia:** the registry reports a cycle when a fiber is inserted: it searches the declared `provide`/`inject` of live fibers and logs a warning naming the cycle; the fiber stays `Pending`. See [Lifecycle](/docs/development-lifecycle).
</Callout>

## Dependency typing and versioning (§6.6)

Linking is purely **nominal** (by key). There are two problems across independently built components:

- **interface drift**: the provider changes the interface behind `k` between versions;
- **key collision**: unrelated providers choose the same key name.

Approaches:

1. **key namespacing** `K × P` (by package; eliminates collisions, couples to a registry);
2. **peer dependencies** with semver ranges through the package manager (Cordis's current approach; relies on semver discipline and one version per package);
3. **structural compatibility** predicates (width subtyping is easy; behavioural contracts are hard; bounded quantification is undecidable).

This is an open problem.

**[Rust]** Rust's `TypeId`/type-keyed services give collision-freedom *within one binary* (a form of key namespacing), but across dynamically loaded modules `TypeId` is not stable, so keys must then be strings plus an ABI/version tag.

<Callout type="info">
**In kardia:** keys are strings (`Service::NAME`) everywhere, because configuration names services. A binding holds its value as `dyn Any`, and a typed access downcasts it, failing with `AccessError::TypeMismatch`, which detects collisions between unrelated types within one binary. Guest modules do not share Rust types with the host: they provide and read services by string key, as JSON views with JSON calls, through the JSON guest ABI. That ABI carries no version tag. See [Services](/docs/guide-services) and [Guest plugins](/docs/guide-guests).
</Callout>

## Co-design with languages and operating systems (§6.7)

- **Languages:** make the context implicit again (for ergonomics, and to prevent a component from reaching another component's context through a closure or a global, which would leak effects out of its lifecycle); give the compiler syntax for effects (compile an effect iterator into one state machine holding the inverses in its frame instead of a closure per step); admit the coeffect specification into the type system (report cycles at compile time; structural dependency comparison à la row types).
- **Operating systems:** make the declared coeffect specification the whole of what a component can reach (like WASM imports), provide isolation and interception natively, and provide OS resources (memory, file descriptors) as coeffects so that acquisitions are recorded once by the party that hands them out; transactional or copy-on-write storage can make some emissions revertible.

## Related work (§7)

| Area | Representative work | Distinction from Cordis |
|---|---|---|
| Monadic effect systems | ZIO, Effect-TS, fp-ts | Require writing inside the effect type; a withdrawn service leaves its effects in place. Cordis is an overlay on ordinary code and pairs every effect with an inverse. |
| Algebraic effects as capabilities | Effekt | Purpose (interpretation vs. tracking and reversion) and setting (static vs. runtime). |
| Reversible effect semantics | Heunen et al. (dagger/inverse arrows) | Global two-sided reversibility vs. a per-atomic-effect one-sided inverse supplied at application. |
| Graded types | Granule, coeffects for Java-like languages | Static annotations over fixed scopes. |
| Context-oriented programming | COP layers | Changes method dispatch in dynamic extents; no tracking or reversion; activation is not dependency-driven. Cordis can express only COP's global, value-driven fragment. |
| Aspect-oriented programming | AspectJ, dynamic AOP | Oblivious quantification vs. declared coeffects; Cordis's crosscutting is bound to a component's lifecycle. |
| Stateful forward migration | Quiescence/tranquility, DSU (Ginseng, Kitsune), Erlang `code_change`, Webpack/Vite HMR | Migrate state forward through hand-written functions; Cordis reverts and reapplies from a clean slate (in-memory state survives only in longer-lived dependencies; DSU-style migration on top of revertible effects is future work), but needs no migration code and supports full unloading. |
| Developer-authored recovery | OSGi/IDE unload callbacks, Command pattern, sagas, effect-handler finalizers, event sourcing, React `useEffect` | The inverse is an unenforced duty decoupled from the operation; `useEffect` pairs them but is not composable (top level only, no async or iterator). |
| Statically scoped reversal | STM, reversible computing (Janus), RCCS, linear types, **RAII, Rust ownership** | Scope and reach are fixed statically. Cordis treats lexical resource management as *complementary*, appropriate for local resources within a component. |
| Interposed reclamation | Nooks, shadow drivers, Akeso | The platform fixes what can be recorded; Cordis lets components introduce their own effects with inverses and propagates removal to dependents. |
| Initialization-time DI | Spring, Guice, Angular, Inversify, Vue provide/inject, React Context | No reactive re-resolution, no lifecycle management. |
| Availability-reactive components | OSGi Declarative Services, iPOJO, R-OSGi | The closest precedent, but with hand-written, synchronous deactivation callbacks. Cordis reverts automatically and runs asynchronous teardown to completion (inertial Unloading). |
| Value-level reactivity | FRP, signals | Value granularity and glitch freedom per turn; Cordis is component-granular with an asynchronous lifecycle. Complementary (a coeffect may carry signals). |

**[Rust] note on RAII:** the paper explicitly positions Rust's ownership/RAII as *statically scoped* reversal: complementary, not a substitute. A Rust port should therefore *not* try to make a component's lifetime a lexical scope; component lifetime is dynamic and governed by the fiber state machine, while `Drop` remains useful for resources local to one effect.

<Callout type="info">
**In kardia:** an `EffectHandle` does not dispose its effect on `Drop`; an effect lives until its fiber unloads or it is disposed explicitly, so a component's lifetime is never tied to a Rust scope. Inside an effect, ordinary `Drop` types still clean up local resources. See [Effects](/docs/guide-effects) and [Lifecycle](/docs/development-lifecycle).
</Callout>

## Conclusion (§8)

Revertible effects give local temporal composability ([Revertible effects](/docs/concepts-revertible-effects)); reactive coeffects give local spatial composability ([Reactive coeffects](/docs/concepts-reactive-coeffects)); the context paradigm and observational equivalence give independence ([The context paradigm](/docs/concepts-context-paradigm)); the calculus ([A calculus of dynamic composition](/docs/concepts-calculus)) lifts both to whole systems with preservation, recovery exactness, ordering, coherence, progress and confluence ([Metatheory](/docs/concepts-metatheory)). Cordis realises this ([Implementation in the paper](/docs/concepts-implementation)); Koishi validates it. The future validation target is **self-evolving agent harnesses**, which stress complete recovery under rapid replacement and dependency coordination under frequent topological change.
