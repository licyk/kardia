本页概述论文（[arXiv:2608.25512](https://arxiv.org/abs/2608.25512)）的 §6–8：理论与设计指导。论文中与 Rust 移植相关的论述在原摘要中标记为 **[Rust]**；本页在每一处之后都附有一个“在 kardia 中”的提示框，说明 kardia 如何实现它。

## 系统边界（§6.1）

边界把环境分为**内部**位置（系统能够独占地修改它们，*并且*能够恢复它们，因此它们被追踪、可撤销）和**外部**位置（任一能力缺失，因此操作表现为 `id_Γ`，不被追踪）。

- **余效应（coeffect）移动边界**：它把一个外部位置具体化到一组各自带有逆操作的操作之后。边界是*按位置*划定的，而不是按介质（私有的临时文件在内部；共享路径在外部）。
- **获取与外发**。触及外部分两个阶段：*获取*（acquisition）在边界内设置一条记录（`open` → 描述符，`malloc` → 内存块，`fork` → 子进程），这是可撤销的；*外发*（emission）通过该通道推送数据（`write`、`send`）并跨越到外部，这是不可撤销的。
- **暂扣与补偿**。要恢复一次外发，要么暂扣它直到产生它的状态确定下来（输出提交问题），要么进行补偿（删除创建的文件、退还扣款），补偿只在应用提供的、更粗的等价意义下成立。补偿像逆操作一样按 LIFO 组合，但交换性元理论（[元理论](/docs/concepts-metatheory)）必须针对这一更粗的关系重新建立。

## 服务多路复用（§6.2）

余效应与 OSGi 服务相呼应：提供者以某个接口发布，消费者进行绑定。多个实现可以通过以下方式实现：

1. **独占绑定**：同一时刻至多绑定一个；切换时卸载一个提供者再加载另一个，会扰动每个消费者。
2. **服务代理**（service broker）：一个中心服务同时被后端提供者和消费者依赖声明（inject）；提供者通过可撤销效应*向代理注册*；后端提供者变化时，消费者看不到任何变化。

代理使以下能力成为可能：**负载均衡**（按策略分派；通过加载和卸载提供者来扩缩容）、**滚动更新**（加载新提供者、转移流量、旧提供者排空后将其卸载：quiescence/tranquility），以及**跨进程调用**（每个进程承载自己的上下文；RPC 保持接口不变；必须按*异步*契约设计）。

**[Rust]** 在单一提供者的演算中，代理模式是让一个键拥有多个提供者的推荐方式。

<Callout type="info">
**在 kardia 中**：每个键在每个领域（realm）中只有一个提供者（第二次 `ctx.provide` 会以 `KardiaError::AlreadyProvided` 失败）。代理是一个普通服务，其注册表是一个 `IdTable`；后端提供者通过在自己的纤程（fiber）上创建的效应（`svc.caller().effect(..)`）向它注册，因此该提供者卸载时注册会被撤回。kardia 没有为访客插件（guest plugin）单独提供代理服务：每个访客纤程的 `GuestService` 就是它自己的 RPC 端点，其调用是同步的，而不是上文所说的异步契约，因此一个挂起的访客会阻塞其调用者。见[服务](/docs/guide-services)与[访客插件](/docs/guide-guests)。
</Callout>

## 访问控制与沙箱（§6.3）

- **基于能力的访问控制**。经代理中介的访问只允许已声明的依赖（未声明的访问是错误）。`inject` 充当能力请求，上下文代理充当能力中介。由于声明是静态的，编排器可以在加载时审查它们。
- **通过拦截（interception）实现细粒度策略**：例如，一个文件系统依赖携带关于可读和可写路径的元数据，由提供者检查。它可以从上下文进行调整而无需修改提供者；它影响的是依赖如何被使用，而不是依赖是否被满足，因此可以在运行时改变而无需重新加载。
- **沙箱化**不受信任的代码需要一个超越语言的执行边界（SFI、独立的运行时、沙箱进程、容器）；不受信任的组件通过一个*桥*访问宿主（host）的依赖，而这个桥本身是一个普通纤程，其能力可以被削减。

## 语言无关性与语言选择（§6.4）[Rust]

**时间方面的要求**：闭包（逆操作是一个被捕获的值），以及一种在运行时引入和撤回组件代码的方式：

- 托管运行时：一个可编程的模块注册表（Node 的 `require.cache`；ESM 没有公开的驱逐 API）；
- **原生代码：显式的动态链接与卸载**（`dlopen`/`dlclose`、`LoadLibrary`/`FreeLibrary`）；
- **WebAssembly**：当原生嵌入者（例如 **Wasmtime**）丢弃实例时，该实例被释放。

在所有情况下，加载都是一个效应（effect），其逆操作撤销模块所引入的注册。

<Callout type="info">
**在 kardia 中**：`kardia-hmr` 通过三种后端加载访客模块，每种后端都通过一个桥插件运行访客插件：桥插件为每个纤程实例化一次访客，并在纤程被释放时丢弃该实例。`WasmSource` 在 Wasmtime 上运行核心 WebAssembly 模块（沙箱化，每个纤程一个 store）。`DylibSource` 加载动态库但从不卸载它们（不调用 `dlclose`）：一旦 Rust 代码注册了线程局部析构函数或交出了 `'static` 引用，卸载它就是不健全的，因此每个版本都从文件的一份新副本加载。`ProcessSource` 为每个纤程运行一个子进程，并在 `dispose` 之后将其终止。见[访客插件](/docs/guide-guests)与[热重载](/docs/guide-hot-reload)。
</Callout>

**空间方面的要求**：两个层面的依赖注入机制：

- **类型层面**：类型正确的依赖访问；上下文类型必须记录每个键的余效应。*类型类（Haskell）和 **trait（Rust）** 让提供者可以在自己的模块中通过实例/`impl` 扩展上下文类型*；TypeScript 使用模块扩充（module augmentation）。
- **运行时层面**：访问必须被动态中介（JavaScript `Proxy`、Python 描述符，或以牺牲类型安全为代价的反射）。
- **元编程**同时提供两者：*编译期元编程（例如 **Rust 过程宏**、Scala 宏、Zig comptime）为每个依赖生成一个带类型的声明以及一个访问器，从而无需通用的拦截原语。*

<Callout type="info">
**在 kardia 中**：`Service` trait 把一个类型绑定到它的键（`#[derive(Service)]`），服务 crate 通过 `Svc<S>` 上的扩展 trait（例如为 `Svc<Timer>` 实现的 `TimerExt`）扩展消费者能做的事，由于该 trait 是本地定义的，一致性规则（coherence）允许这样做。访问在运行时由 `ctx.get::<S>()` 针对已提交视图（committed view）中介，无需代理。`#[plugin]` 宏提供编译期的那一半：接收 `Injected<(A, B)>` 的插件函数声明了 `A` 和 `B`，通过它访问其他任何东西都无法通过编译。见[插件](/docs/guide-plugins)、[服务](/docs/guide-services)与 [API 设计](/docs/development-design)。
</Callout>

## 相互依赖与组件粒度（§6.5）

依赖环会让涉及的组件**永久处于未激活状态**。与并发死锁不同，它*可以从声明中预测*，因此运行时可以在加载时报告它。大多数环都可以分解：例如，server ↔ access-controller 可以拆成 `server-core`、`access-control-core`、`request-mediation`（依赖两个核心）和 `policy-management`（依赖两者）。代价是集成组件的数量可能呈平方增长，可以通过打包、基于约定的装配和脚手架来缓解。

<Callout type="info">
**在 kardia 中**：注册表在纤程插入时报告依赖环：它在存活纤程声明的 `provide`/`inject` 中搜索，并记录一条指明该环的警告；该纤程保持 `Pending`。见[生命周期](/docs/development-lifecycle)。
</Callout>

## 依赖类型与版本管理（§6.6）

链接是纯**名义**的（按键）。在独立构建的组件之间有两个问题：

- **接口漂移**：提供者在不同版本之间改变了 `k` 背后的接口；
- **键冲突**：互不相关的提供者选择了相同的键名。

可选的方法：

1. **键命名空间** `K × P`（按包划分；消除冲突，但与注册中心耦合）；
2. 通过包管理器使用带 semver 范围的 **peer 依赖**（Cordis 当前的做法；依赖 semver 纪律，且每个包只有一个版本）；
3. **结构兼容性**谓词（宽度子类型容易；行为契约困难；有界量化不可判定）。

这是一个开放问题。

**[Rust]** Rust 的 `TypeId`/以类型为键的服务*在单个二进制内*避免了冲突（一种键命名空间），但在动态加载的模块之间 `TypeId` 并不稳定，因此此时键必须是字符串加上一个 ABI/版本标签。

<Callout type="info">
**在 kardia 中**：键在所有地方都是字符串（`Service::NAME`），因为配置要按名称引用服务。绑定以 `dyn Any` 保存其值，类型化访问会对它做向下转型（downcast），类型不符时以 `AccessError::TypeMismatch` 失败，从而在单个二进制内检测互不相关类型之间的冲突。访客模块不与宿主共享 Rust 类型：它们按字符串键提供和读取服务，以 JSON 视图和 JSON 调用的形式，经由 JSON 访客 ABI 进行。该 ABI 不携带版本标签。见[服务](/docs/guide-services)与[访客插件](/docs/guide-guests)。
</Callout>

## 与语言和操作系统的协同设计（§6.7）

- **语言**：让上下文重新变得隐式（为了易用性，也为了防止组件通过闭包或全局变量触及另一个组件的上下文，那会把效应泄漏到其生命周期之外）；为效应提供编译器语法（把效应迭代器编译成一个在其栈帧中保存逆操作的状态机，而不是每一步一个闭包）；把余效应规约纳入类型系统（在编译期报告依赖环；类似行类型（row types）的结构化依赖比较）。
- **操作系统**：让声明的余效应规约成为组件所能触及的全部（类似 WASM 的导入），原生提供隔离（isolation）与拦截，并把操作系统资源（内存、文件描述符）作为余效应提供，使获取由分发资源的一方一次性记录；事务式或写时复制的存储可以使某些外发变得可撤销。

## 相关工作（§7）

| 领域 | 代表性工作 | 与 Cordis 的区别 |
|---|---|---|
| 单子效应系统 | ZIO、Effect-TS、fp-ts | 要求在效应类型内部编写代码；撤回的服务会把其效应留在原处。Cordis 是叠加在普通代码之上的一层，并为每个效应配对一个逆操作。 |
| 作为能力的代数效应 | Effekt | 目的不同（解释 vs. 追踪与撤销），场景不同（静态 vs. 运行时）。 |
| 可逆效应语义 | Heunen 等人（dagger/逆箭头） | 全局的双向可逆性 vs. 在应用时提供的、针对每个原子效应的单侧逆操作。 |
| 分级类型 | Granule、面向类 Java 语言的余效应 | 固定作用域上的静态标注。 |
| 面向上下文编程 | COP 层 | 在动态范围内改变方法分派；没有追踪或撤销；激活不是由依赖驱动的。Cordis 只能表达 COP 中全局的、由值驱动的那一部分。 |
| 面向切面编程 | AspectJ、动态 AOP | 无感知的量化 vs. 声明的余效应；Cordis 的横切关注点绑定在组件的生命周期上。 |
| 有状态的前向迁移 | Quiescence/tranquility、DSU（Ginseng、Kitsune）、Erlang `code_change`、Webpack/Vite HMR | 通过手写的函数把状态向前迁移；Cordis 从干净状态撤销并重新应用（内存中的状态只在生命周期更长的依赖中保留；在可撤销效应之上实现 DSU 式迁移是未来工作），但不需要迁移代码，并支持完全卸载。 |
| 开发者编写的恢复 | OSGi/IDE 卸载回调、命令模式、saga、效应处理器的终结器、事件溯源、React `useEffect` | 逆操作是一项与操作脱钩、不被强制执行的职责；`useEffect` 把二者配对，但不可组合（只能在顶层，不支持异步或迭代器）。 |
| 静态作用域的撤销 | STM、可逆计算（Janus）、RCCS、线性类型、**RAII、Rust 所有权** | 作用域和触及范围在静态时确定。Cordis 把词法式的资源管理视为*互补*的，适用于组件内部的局部资源。 |
| 插入式回收 | Nooks、shadow drivers、Akeso | 平台固定了可记录的内容；Cordis 让组件引入自己的、带有逆操作的效应，并把移除传播到依赖者。 |
| 初始化时依赖注入 | Spring、Guice、Angular、Inversify、Vue provide/inject、React Context | 没有响应式的重新解析，也没有生命周期管理。 |
| 可用性响应式组件 | OSGi Declarative Services、iPOJO、R-OSGi | 最接近的先例，但使用手写的同步停用回调。Cordis 自动撤销，并把异步拆除运行到完成（惯性（inertia）的 Unloading）。 |
| 值级响应式 | FRP、signals | 值粒度，每轮无毛刺；Cordis 是组件粒度，带异步生命周期。二者互补（余效应可以携带 signal）。 |

**关于 RAII 的 [Rust] 说明**：论文明确把 Rust 的所有权/RAII 定位为*静态作用域*的撤销：它是互补的，而不是替代品。因此 Rust 移植*不应*试图把组件的生命周期做成一个词法作用域；组件的生命周期是动态的，由纤程状态机管理，而 `Drop` 仍适用于单个效应内部的局部资源。

<Callout type="info">
**在 kardia 中**：`EffectHandle` 在 `Drop` 时不会释放其效应；效应一直存在，直到其纤程卸载或它被显式释放，因此组件的生命周期从不绑定到某个 Rust 作用域。在效应内部，普通的 `Drop` 类型仍会清理局部资源。见[效应](/docs/guide-effects)与[生命周期](/docs/development-lifecycle)。
</Callout>

## 结论（§8）

可撤销效应带来局部时间可组合性（[可撤销效应](/docs/concepts-revertible-effects)）；响应式余效应带来局部空间可组合性（[响应式余效应](/docs/concepts-reactive-coeffects)）；上下文范式与观察等价带来独立性（[上下文范式](/docs/concepts-context-paradigm)）；演算（[动态组合演算](/docs/concepts-calculus)）把二者提升到整个系统，并具有保持性、恢复精确性、顺序性、一致性、进展性与合流性（[元理论](/docs/concepts-metatheory)）。Cordis 实现了这一切（[论文中的实现](/docs/concepts-implementation)）；Koishi 验证了它。未来的验证目标是**自我演化的智能体框架**（self-evolving agent harnesses），它们对快速替换下的完全恢复，以及频繁拓扑变化下的依赖协调提出了严峻考验。
