**Guest plugins** are separate modules that the [`hmr` plugin](/docs/guide-hot-reload) can reload in place, unlike plugins compiled into the binary, whose code changes need a restart. In a config file loaded by the `kardia` binary, any entry name that is not a built-in plugin is a guest module path, relative to the config file:

```yaml
- id: hello
  name: ./plugins/hello.wasm
  config: { greeting: hi }
```

All backends speak one JSON-based **guest ABI** (below) and run each guest plugin through a bridge plugin that instantiates the guest once per fiber and drops the instance when the fiber is disposed. The Rust SDK `kardia-guest` writes such guests for every backend from one source.

## Backends [#backends]

| | WebAssembly (`WasmSource`) | Dynamic library (`DylibSource`) | Child process (`ProcessSource`) |
|---|---|---|---|
| Files | `.wasm`, or `.wat` text | `.so` / `.dylib` / `.dll` | executables |
| Runs | on wasmtime, one store per fiber | in the host process | one child process per fiber |
| Isolation | sandboxed, with optional fuel, time and memory limits | none: a crash in the library brings down the app | a crashing guest fails only its own plugin |
| Reload | compiles once per version; old and new instances run side by side, and dropping an instance releases all of its memory | each version is loaded from a fresh copy and **never unloaded**; it stays loaded until the process exits | reloading a module respawns its processes |
| Use for | production guests | development: same toolchain, no WASM target needed | guests in any language, or that must not crash the host |
| `kardia` binary | yes | yes | not yet (library only) |

**WebAssembly.** `WasmSource` runs core WebAssembly modules on wasmtime rather than WIT components, so guests need no component toolchain (the tests are written in WAT). A module compiles once per version and instantiates in its own store per fiber. `WasmSource::with_limits` bounds each instance:

```rust
use kardia::hmr::{WasmLimits, WasmSource};

let source = WasmSource::with_limits(
    WasmLimits::new()
        .fuel(10_000_000)                    // per export, about one unit per instruction
        .timeout(Duration::from_secs(5))     // per export, by epoch interruption
        .memory(64 << 20),                   // the most linear memory, in bytes
);
```

An export that runs out of fuel or time traps, and the instance fails its later calls with `the guest was stopped: …`; growing memory past the cap traps. With a timeout, a caller's own deadline ([`call_timeout`, `call_async`](#guest-service)) is honoured too. None of the limits is set by `WasmSource::new()`. Each of these failures is a typed [`GuestFailure`](#guest-failure).

To give a WASM plugin's metadata from outside, as `ProcessGuest::plugin` does, compile the module into a `WasmGuest`: `WasmGuest::new(bytes, limits)` compiles WASM bytes or WAT text on an engine of its own, and `source.guest(bytes)` on a `WasmSource`'s engine, with its limits. Neither instantiates the module. `plugin(meta)` makes the plugin, and each instance must declare the same metadata when it starts; `module(id)` reads the metadata from an instance instead, as `WasmSource` does.

```rust
use kardia::hmr::{GuestMeta, WasmGuest, WasmLimits};

let guest = WasmGuest::new(std::fs::read("greeter.wasm")?, WasmLimits::new().fuel(10_000_000))?;
let plugin = guest.plugin(GuestMeta::new("greeter").provide("greeter"));
```

**Trap handling on macOS**. wasmtime handles WASM traps on macOS through Mach exception ports by default. Its trap handler is process-wide: wasmtime installs it with the first engine, and panics when a later engine asks for the other setting. `kardia::hmr::set_macos_mach_ports(false)` has every engine kardia-hmr makes use Unix signals instead. Call it before the first `WasmSource` or `WasmGuest` is made: after that, asking for the other setting returns an error and changes nothing. An engine the application makes with wasmtime itself must use the same setting. Elsewhere than macOS the call changes nothing.

**Dynamic libraries.** `DylibSource` speaks a C ABI instead of passing Rust types: a `cdylib` carries its own copies of `kardia-core` and tokio, with separate statics and no runtime context. Each load copies the library to a fresh path (in a `kardia-dylib-<pid>` directory under the temp directory), because the platform loader hands out the library it already loaded for a known path. Libraries are never unloaded: unloading Rust code is unsound once it registered thread-local destructors or handed out `'static` references.

**Child processes.** `ProcessSource` runs each plugin instance as its own process, speaking the guest ABI as JSON lines over stdin and stdout (see [Process transport](#process)). A guest whose process ends fails only its own plugin; one that breaks the protocol or outlives a call's deadline is killed. [Process guests](#process-guests) covers arguments, spawners, timeouts and exit reports. Replace an executable by renaming a new file over it: a running executable cannot be written to, and one held open for writing cannot be started.

**Common to all three.** `GuestService::call` blocks its caller until the guest answers; `call_async` runs the call off the async workers, as the bridge does with `apply` and `dispose`. A deadline stops a process guest (it is killed) and a WASM guest with a time limit (it traps); a dylib guest runs on the caller's thread and cannot be stopped. There is no separate broker service: each fiber's `GuestService` is the RPC endpoint. The backends are cargo features of `kardia-hmr` (`wasm`, `dylib`, `process`, all on by default), beside `preserve-order` (on by default), which turns on `serde_json/preserve_order` through `kardia-loader`; leave it off to keep serde_json's default maps in your application ([Key order](/docs/development-loader#loader)).

The `kardia` binary picks a backend by file extension: `.wasm` and `.wat` go to `WasmSource`, anything else to `DylibSource`. An app built on the library chooses its own:

```rust
use kardia::hmr::{DylibSource, ModuleCode, ModuleSource, ProcessSource, WasmSource};

/// Guest modules by extension: WASM, executables in `bin/`, else a dynamic library.
struct GuestFiles {
    wasm: WasmSource,
}

impl ModuleSource for GuestFiles {
    fn load(&self, id: &str) -> Result<ModuleCode> {
        let path = Path::new(id);
        match path.extension().and_then(|ext| ext.to_str()) {
            Some("wasm" | "wat") => self.wasm.load(id),
            _ if path.parent().is_some_and(|dir| dir.ends_with("bin")) => ProcessSource.load(id),
            _ => DylibSource.load(id),
        }
    }
}

let graph = ModuleGraph::new(GuestFiles { wasm: WasmSource::new() });
```

## Calling guests from Rust [#guest-service]

A guest provides services with `Host::provide`. On the host side, each is a `kardia::hmr::GuestService`, whose JSON view is the value the guest provided:

```rust
use kardia::hmr::GuestService;

let counter = ctx.get_as::<GuestService>("counter")?;     // checked access, by key
println!("{}", counter.value());                          // the provided JSON value
let count = counter.call("increment", json!(null))?;      // calls the guest's `call`
let view = ctx.view("counter")?;                          // the JSON view alone
```

| `GuestService` | |
|---|---|
| `value()` | the JSON value the guest provided the service with |
| `call(method, args)` | calls the guest's `cordis_call` with `{ key, method, args }` and returns its JSON result; blocks until the guest answers, or until the guest's default timeout |
| `call_timeout(method, args, timeout)` | like `call`, failing after `timeout` with `the guest did not answer in time`; a process guest is then killed, and its later calls fail |
| `call_async(method, args, timeout)` | the call off the async workers, with an optional timeout; dropping the future cancels the call (a `kardia-guest/2` guest is told, and its result is dropped) |
| `is_available()` | whether the instance can still answer: it is not disposed, and its process has not exited |
| `handle()` | the [`GuestHandle`](#exit) of a process guest |

A call fails with `the guest instance is disposed` once the providing fiber is gone, with `the guest process exited` once a process guest has ended on its own, and with `invalid result of <key>.<method>: …` if the guest returns something that is not JSON. A guest calling back into an instance that is already running on the same thread (directly or through other guests) fails with `re-entrant call into a guest instance` instead of deadlocking. Like any service, a guest service is withdrawn when the guest's fiber is disposed.

## Process guests [#process-guests]

`ProcessSource` runs a module id as a program with no arguments. `ProcessGuest` describes one guest command with its options; use it directly, or in a `ModuleSource` of your own:

```rust
use kardia::hmr::{GuestCommand, GuestMeta, ProcessGuest};

let guest = ProcessGuest::new(
    GuestCommand::new("python3").arg("plugin.py").env("PLUGIN_ROOT", &root).current_dir(&data),
)
.spawner(MySpawner)                          // default: StdSpawner
.timeout(Duration::from_secs(30))            // each export, unless its caller sets a deadline
.frame_limit(1 << 20);                       // the longest line the guest may send

// metadata from the caller: building the plugin starts nothing
let plugin = guest.plugin(GuestMeta::new("jira").provide("jira"));
let fiber = ctx.plugin_def(&plugin, config)?;

// or metadata from the guest, as ProcessSource reads it
let module = guest.module("plugins/jira")?;
```

| `ProcessGuest` | |
|---|---|
| `new(command)` | a guest running `command` (a `GuestCommand`: program, `arg`/`args`, `env`, `current_dir`) |
| `spawner(spawner)` | who starts its processes (below); `StdSpawner` by default |
| `timeout(duration)` | how long each export may take when its caller sets no deadline; past it the process is killed. None by default, but `dispose` is then bounded to 5 seconds |
| `handshake_timeout(duration)` | how long the guest has to answer the [handshake](#process) (10 seconds by default) |
| `frame_limit(bytes)` | the longest line the guest may send (16 MiB by default); a longer one kills the guest |
| `plugin(meta)` | the guest's plugin, with a `GuestMeta` (`new(name)`, `.inject(key)`, `.provide(key)`) from the caller. Each process must declare the same metadata (name, and the same services in any order) when it starts, or its fiber fails |
| `module(id)` | the guest's module, with its metadata read from a process started for it |

### Spawners [#spawner]

A `Spawner` starts the processes, so the app decides how a guest runs (a sandbox, a process group, a process manager that owns it):

```rust
pub trait Spawner: Send + Sync + 'static {
    fn spawn(&self, command: &GuestCommand) -> io::Result<GuestProcess>;
}
```

It gets the command's program, arguments, environment variables and working directory (`get_program`, `get_args`, `get_envs`, `get_current_dir`, or `to_std()` for a `std::process::Command`), and returns a `GuestProcess`: its stdin and stdout, optionally its stderr (`.stderr(…)`, for the [exit report](#exit)), and a `GuestChild`, the control the instance keeps until the process has ended (`id`, `kill`, `try_wait`, `wait`, as `std::process::Child` has them). `GuestProcess::from_child` takes a `std::process::Child` spawned with piped stdio. `StdSpawner`, the default, runs the command with `std::process` in the app's environment plus the command's variables. The instance kills its process when it is done with it, on dispose or when the guest fails.

### Exit reports [#exit]

Each process guest has a `GuestHandle`, from `GuestService::handle()` or the `GuestStarted` event:

| `GuestHandle` | |
|---|---|
| `id()` | the process id the spawner reported |
| `protocol()` | the protocol the guest speaks: `1` or `2` (`kardia-guest/2`) |
| `exit()` | the `GuestExit` report, once the process has ended |
| `subscribe()` | a `tokio::sync::watch` receiver of the report (`None` while the process runs) |
| `exited()` | a future resolving with the report |
| `stderr_tail()` | the last 16 KiB the process wrote to stderr so far |
| `kill()` | kills the process; its report says `killed by the host` |
| `ping(timeout)` | checks that a `kardia-guest/2` guest answers, even while it runs a call; resolves with the round trip |

A `GuestExit` has the exit `status`, its `cause` (`ExitCause::Exited` on its own, `Killed(reason)` for a missed deadline, a protocol violation or `kill()`, `Disposed` by its fiber) and the `stderr_tail` (16 KiB). stderr lines are also logged as the plugin at `debug`.

The bridge emits two events on the guest's fiber: `GuestStarted { fiber, handle }` once the process has started, before `apply`, and `GuestExited { fiber, exit }` when it ends before the fiber disposes it. The fiber then fails with the report as its error (`Fiber::fail`), which withdraws its services, so their consumers wait for them again. As for any failed fiber, `restart` keeps it failed; `fiber.update(config)` starts a new process.

```rust
use kardia::hmr::GuestExited;

ctx.on(|event: &GuestExited| {
    let tail = String::from_utf8_lossy(&event.exit.stderr_tail);
    eprintln!("{} ended: {}\n{tail}", event.fiber.name(), event.exit);
})?;
```

## Custom transports [#transports]

The backends implement two public traits, which a host can implement for a transport of its own:

| | |
|---|---|
| `GuestCode::instantiate(&self, host: GuestHost) -> Result<Box<dyn GuestInstance>>` | starts an instance whose host calls act on `host` (`log`, `provide`, `view`, `invoke`); called off the async workers |
| `GuestInstance::call(&mut self, export, input, control: &CallControl) -> Result<Vec<u8>>` | calls an `Export` (`Meta`, `Apply`, `Call`, `Dispose`) with UTF-8 JSON input, returning the guest's output or its error; it should stop at `control.deadline()` and drop a result once `control.is_cancelled()` (`on_cancel` wakes it) |
| `GuestInstance::handle(&self) -> Option<GuestHandle>` | the process behind it, if any (`None` by default) |

`kardia::hmr::guest_module(id, code)` turns a `GuestCode` into module code, reading its metadata from a fresh instance; `guest_plugin(code, meta)` turns it into a plugin with metadata from the caller. `ProcessGuest` and `WasmGuest` are the process and WASM backends' `GuestCode`; their `plugin(meta)` and `module(id)` are these two. A transport whose instance fails should return a [`GuestFailure`](#guest-failure), so its callers can tell that failure from the guest's own errors.

## Writing a guest in Rust [#sdk]

`kardia-guest` is licensed under MIT OR Apache-2.0, unlike the rest of kardia (GPL-3.0-only), so a guest that links it chooses its own licence.

Create a `cdylib` crate that depends on `kardia-guest`:

```toml
[lib]
crate-type = ["cdylib"]

[dependencies]
kardia-guest = "0.2"
```

Implement `Guest` and `export!` it:

```rust
use kardia_guest::{Guest, Host, Level, Map, Meta, Request, Result, Value, json};

struct Counter {
    count: u64,
}

impl Guest for Counter {
    type Config = Value;

    fn meta() -> Meta {
        Meta::plugin("counter").provide("counter")
    }

    fn apply(host: &Host, config: Value, _imports: Map<String, Value>) -> Result<Self> {
        host.provide("counter", &json!({ "config": config }))?;
        host.log(Level::Info, "counting");
        Ok(Counter { count: 0 })
    }

    fn call(&mut self, _: &Host, request: Request) -> Result<Value> {
        match request.method.as_str() {
            "increment" => {
                self.count += 1;
                Ok(json!(self.count))
            }
            method => Err(format!("unknown method {method}").into()),
        }
    }
}

kardia_guest::export!(Counter);
```

### The `Guest` trait [#guest-trait]

Each fiber running the plugin gets its own instance of the type.

| Item | Purpose |
|---|---|
| `type Config: DeserializeOwned` | the plugin's configuration; `null` decodes as `{}` when it fails to decode as it is |
| `fn meta() -> Meta` | what the module depends on and exports |
| `fn apply(host, config, imports) -> Result<Self>` | starts an instance with its configuration and the values of the module's dependencies (keyed by resolved path) |
| `fn call(&mut self, host, request) -> Result<Value>` | answers a call to a service the instance provided; the default fails with `<key> has no method <method>` |
| `fn dispose(self, host)` | runs when the fiber is disposed, before the instance is dropped; the default does nothing |

`Meta` describes the module:

| `Meta` | |
|---|---|
| `Meta::plugin(name)` | a module exporting a plugin named `name` |
| `Meta::value(value)` | a module exporting a value, which dependent modules receive as an import |
| `.dep(path)` | a dependency: a module path relative to this module |
| `.inject(key)` | a service the plugin reads; it starts once the service is available |
| `.provide(key)` | a service the plugin provides |

`Request` is `{ key, method, args }`. `Error` is an error message reported to the host (`Error::msg(..)`, `error.message()`); any displayable error converts into it with `?`.

### The `Host` [#host]

| `Host` method | Does |
|---|---|
| `log(level, text)` | logs as the plugin (`Level::Error` … `Level::Debug`) |
| `provide(key, &value)` | provides the service `key`, whose JSON view is `value`; calls to it arrive at `Guest::call`. It is withdrawn when the fiber is disposed. The key must be declared with `Meta::provide`: the host refuses any other, and provides nothing. |
| `view(key)` | the JSON view of a service declared with `Meta::inject` (or provided by this plugin or its ancestors), with the checked access of the plugin's declared `inject` |
| `invoke(key, method, &args)` | calls a service provided by another guest |
| `cancelled()` | whether the host cancelled the running export, so a long call may stop early; only a process guest served under `kardia-guest/2` is told |

From Rust host code, a guest's services are called through `GuestService` (see [above](#guest-service)).

### Building [#build]

The same source builds a WebAssembly or a dynamic-library guest. `export!` emits the WASM exports on `wasm32` and the C symbols elsewhere:

```sh
rustup target add wasm32-unknown-unknown                # once
cargo build --release --target wasm32-unknown-unknown   # target/wasm32-unknown-unknown/release/<crate>.wasm
cargo build --release                                   # target/release/lib<crate>.so (or .dylib / .dll)
```

For a **process guest**, add a binary to the crate whose `main` serves the guest. Use `crate-type = ["cdylib", "rlib"]`, so that the binary can use the library:

```toml
[lib]
crate-type = ["cdylib", "rlib"]

[[bin]]
name = "my-guest-process"
path = "src/main.rs"
```

```rust
fn main() {
    kardia_guest::serve::<my_guest::Counter>();
}
```

```sh
cargo build --release --bin my-guest-process            # target/release/my-guest-process
```

`serve` answers the exports the host sends as JSON lines on stdin, until the host disposes the instance or stdin closes. It speaks `kardia-guest/2` with a host that offers it, and protocol version 1 with any other: a thread then reads stdin, so pings are answered while an export runs and `Host::cancelled` sees a cancellation. stdout carries the protocol, so a process guest must not print to it; it logs through `Host::log` or to stderr.

### Modules with dependencies [#deps]

A module can depend on other modules, and a module can export a value instead of a plugin:

```rust
// shared.rs, built as shared.wasm: exports a value
impl Guest for Shared {
    type Config = Value;
    fn meta() -> Meta {
        Meta::value(json!({ "greeting": "hello" }))
    }
    fn apply(_: &Host, _: Value, _: Map<String, Value>) -> Result<Self> {
        Ok(Shared)
    }
}

// greeter.rs, built as greeter.wasm next to it
impl Guest for Greeter {
    type Config = Value;
    fn meta() -> Meta {
        Meta::plugin("greeter").dep("./shared.wasm")
    }
    fn apply(host: &Host, _: Value, imports: Map<String, Value>) -> Result<Self> {
        let shared = imports.values().next().cloned().unwrap_or_default();  // keyed by resolved path
        host.log(Level::Info, shared["greeting"].as_str().unwrap_or("hi"));
        Ok(Greeter)
    }
}
```

When `shared.wasm` changes, hot reload reloads `greeter` too, since it imports the changed module (see [Reconcile transactions](/docs/guide-hot-reload#reconcile)). A module exporting neither a plugin nor a value exports nothing.

## Failure behaviour [#failures]

An error or a panic in a guest fails only that plugin or call:

| Backend | A panic in a guest | The guest goes away |
|---|---|---|
| dylib | the SDK catches it and returns it as an error: `the guest panicked: <message>` | a crash brings down the host |
| process | the SDK catches it and returns it as an error: `the guest panicked: <message>` | a process that exits fails its plugin's fiber with its [exit report](#exit), and its calls fail with `the guest process exited`; one that breaks the protocol (`invalid message from guest: …`), sends a line over the frame limit or outlives a call's deadline (`the guest did not answer in time`) is killed, with the same result |
| WebAssembly | the guest aborts, and the host reports the abort as a failed call | with limits, an export out of fuel or time traps, and the instance fails its later calls |

- An error returned from `apply` fails the plugin's fiber (`Failed`); an error returned from `call` fails that call, and the instance keeps running.
- A panic in `dispose` is contained, as the host has nothing to report it to.
- The process of a disposed or failed instance is never left running; after `dispose`, the host kills it, and `dispose` itself is bounded by the guest's timeout (5 seconds without one). If the host goes away, a process guest exits.
- While the module's metadata is read (`meta`), there is no plugin context: host calls fail with `host calls are unavailable while reading module metadata`.
- A guest provides only the services its metadata declares in `provide`: providing any other fails with `cannot provide "<key>": the plugin does not declare it in provide`, and nothing is provided, so no consumer sees the service, even briefly.

### Typed failures [#guest-failure]

When the guest instance itself fails, rather than the guest reporting an error, the call fails with a `kardia::hmr::GuestFailure`: its `kind` (a `GuestFailureKind`) says how, and its text is the error's message, unchanged. `GuestFailure::of(&error)` finds it in a `kardia_core::Error`, and so does `error.downcast_ref::<GuestFailure>()`. An error the guest reports itself (a failure status, or an error the SDK returns), a missing export, a disposed instance or a call that waited too long for another one to finish is not a `GuestFailure`; the instance keeps running.

| `GuestFailureKind` | When |
|---|---|
| `Trap` | a WASM guest trapped (`wasm trap: …`), or a host function failed while it ran |
| `OutOfFuel` | a WASM export used up its fuel; the instance's later calls fail the same way (`the guest was stopped: …`) |
| `Timeout` | a WASM export was interrupted at its deadline (and the instance's later calls fail the same way), or a process guest was killed at its deadline (`the guest did not answer in time`) |
| `OutOfMemory` | a WASM guest was refused growing its memory (`forcing trap when growing memory …`) |
| `Exited` | the guest process ended on its own (`the guest process exited`, and the fiber's failure, its [exit report](#exit)) |
| `Killed` | the guest process was killed: it broke the protocol, sent a line over the frame limit, a thread serving it panicked, or its host killed it (the fiber fails with its exit report) |
| `Panicked` | a guest call panicked on the host's side, or the WASM epoch thread did (calls with a time limit then fail) |

The threads kardia-hmr starts (a process guest's `guest-stdin`, `guest-stdout` and `guest-stderr` threads, and the `wasm-epoch` thread of an engine with a time limit) catch their panics: a process guest is then killed, with `the <thread> thread panicked: <message>` as the reason of its exit report and of its failed calls. A panic hook that aborts on panics it does not know to be caught can ask `kardia::hmr::is_panic_contained()`, which is true on those threads.

## The guest ABI [#abi]

Guests in other languages implement this interface, which is also documented in the `kardia-hmr` crate docs (`cargo doc -p kardia-hmr --open`).

Data crosses the boundary as UTF-8 JSON in byte buffers. The host keeps one **message** per instance: the input of the export being called, then the result of the last host call. The guest copies it into its own memory with `read`, after allocating the length it was given.

**Exports** (status `0` is success; on failure the guest `write`s the error):

| WASM | dylib | |
|---|---|---|
| `memory` | `cordis_new() -> state` | memory / per-instance guest state |
| `cordis_meta() -> i32` | `cordis_meta(state, host) -> i32` | `write`s `{ deps?, plugin?: { name?, inject?, provide? }, value? }` |
| `cordis_apply(len) -> i32` | `cordis_apply(state, host, len) -> i32` | message: `{ config, imports }` |
| `cordis_call(len) -> i32` | `cordis_call(state, host, len) -> i32` | message: `{ key, method, args }`; `write`s the result |
| `cordis_dispose()` (optional) | `cordis_dispose(state, host)` | last call; a dylib frees `state` |

`deps` are module paths relative to the module; `imports` maps each dependency that exports a `value` to that value. A module exporting neither a plugin nor a value exports nothing.

**Names.** Each export and dylib symbol may also be named `kardia_*` instead of `cordis_*` (`kardia_meta`, `kardia_new`, …). The host looks each one up as `kardia_*` first and falls back to `cordis_*`, so a guest may export either set, mix them, or export both: when both are present the host calls the `kardia_*` one. WASM host functions are offered under both import modules, `kardia` and `cordis`, and a module may import from either or both. Hosts up to kardia-hmr 0.2.0 know only `cordis_*` and `cordis`, so `kardia-guest` (like pykardia's exporter) exports every entry under both names and imports the host functions from `cordis`: its guests load on old and new hosts alike.

**Host functions** (WASM imports from module `cordis` or `kardia`; for a dylib, function pointers in the `host` struct `{ host, read, write, log, provide, view, invoke }`, each taking `host.host` first). Pointers are guest addresses, lengths are byte counts:

- `read(ptr)` copies the message to `ptr`.
- `write(ptr, len)` sets the result of the current export.
- `log(level, ptr, len)` logs as the plugin (`0` error … `3` debug).
- `provide(key, key_len, value, value_len) -> i32` provides the service `key` as a `GuestService` whose JSON view is `value`. A key the plugin's metadata does not declare in `provide` is refused with an error, and nothing is provided.
- `view(key, key_len) -> i32` reads the JSON view of a service, with the checked access of the plugin's declared `inject`.
- `invoke(key, key_len, method, method_len, args, args_len) -> i32` calls a `GuestService`.

Host functions returning `i32` set the message to their result and return its length, or set it to an error message and return `-1 - len`.

**Lifecycle of a module.** Loading a module instantiates it once to read its metadata (`meta`, then `dispose`); dependencies in `deps` are loaded first. Each fiber running the plugin then gets a fresh instance: `apply` with `{ config, imports }`, any number of `call`s, and `dispose` when the fiber is disposed, after which the instance is dropped. A non-zero status with no written output fails with `guest failed with status <n>`.

### Process transport [#process]

A process guest exchanges one JSON object per line over its stdin and stdout (stdout is reserved for this; a guest logs through `log` or stderr). There are two versions: version 1, and `kardia-guest/2`, which adds a handshake, request ids, cancellation and pings.

**Handshake.** The host's first line offers version 2 as an export: `{"export":"hello","input":{"protocol":"kardia-guest/2"}}`. A version 2 guest answers `{"ready":"kardia-guest/2"}`. A version 1 guest answers `{"done":1}`, as it does to any export it does not know, and the host serves it version 1, so either starts without a delay, and a version 2 guest still runs on a host that never offers it. A guest that does not answer within the handshake timeout is killed.

**Version 1:**

| Direction | Message | Meaning |
|---|---|---|
| host → guest | `{ export, input }` | an export: `export` is one of `meta`, `apply`, `call`, `dispose`; `input` is the message (`null` if empty) |
| guest → host | `{ call: "log", level, text }` | logs; no reply |
| guest → host | `{ call: "provide", key, value }` | answered with `{ result }` or `{ error }` (an undeclared `key` is an error) |
| guest → host | `{ call: "view", key }` | answered with `{ result }` or `{ error }` |
| guest → host | `{ call: "invoke", key, method, args }` | answered with `{ result }` or `{ error }` |
| guest → host | `{ output }` | sets the result text of the export |
| guest → host | `{ done: status }` | ends the export |

**`kardia-guest/2`** sends the same messages, each with an `id`: an export carries a new `id`, and every message about it carries the same one (`{"id":3,"call":"view","key":"db"}`, `{"id":3,"result":…}`, `{"id":3,"output":…}`, `{"id":3,"done":0}`). The host calls one export at a time. Two more messages need no running export:

| Direction | Message | Meaning |
|---|---|---|
| host → guest | `{ cancel: id }` | the caller no longer wants export `id`: the guest may stop early; the host drops its result and answers its later host calls with an error |
| host → guest | `{ ping: n }` | answered with `{ pong: n }`, even while an export runs |

After `dispose` the process is killed; a guest exits when its stdin closes.

For example, the `Counter` guest above, applied without configuration and then called once:

```text
→ {"export":"apply","input":{"config":null,"imports":{}}}
← {"call":"provide","key":"counter","value":{"config":null}}
→ {"result":null}
← {"call":"log","level":2,"text":"counting"}
← {"done":0}
→ {"export":"call","input":{"key":"counter","method":"increment","args":null}}
← {"output":"1"}
← {"done":0}
```

The same under `kardia-guest/2`:

```text
→ {"export":"hello","input":{"protocol":"kardia-guest/2"}}
← {"ready":"kardia-guest/2"}
→ {"id":1,"export":"apply","input":{"config":null,"imports":{}}}
← {"id":1,"call":"provide","key":"counter","value":{"config":null}}
→ {"id":1,"result":null}
← {"id":1,"call":"log","level":2,"text":"counting"}
← {"id":1,"done":0}
→ {"id":2,"export":"call","input":{"key":"counter","method":"increment","args":null}}
← {"id":2,"output":"1"}
← {"id":2,"done":0}
```

## A guest by hand: `hello.wat` [#hello]

`examples/plugins/hello.wat` is a guest written by hand in WebAssembly text. It imports `write` and `log` from the `cordis` module and exports `memory` and three functions:

```text
;; A guest plugin in WebAssembly text (see the guest ABI in the kardia-hmr
;; docs). Edit the greeting while the app runs: hmr reloads this module in
;; place, disposing the old instance first.
(module
  (import "cordis" "write" (func $write (param i32 i32)))
  (import "cordis" "log" (func $log (param i32 i32 i32)))
  (memory (export "memory") 1)

  (data (i32.const 0) "{\"plugin\":{\"name\":\"hello\"}}\00")
  (data (i32.const 128) "goodbye from wasm\00")
  (data (i32.const 256) "hello from wasm\00")

  ;; the length of the NUL-terminated string at $ptr
  (func $len (param $ptr i32) (result i32)
    (local $end i32)
    (local.set $end (local.get $ptr))
    (block $done
      (loop $next
        (br_if $done (i32.eqz (i32.load8_u (local.get $end))))
        (local.set $end (i32.add (local.get $end) (i32.const 1)))
        (br $next)))
    (i32.sub (local.get $end) (local.get $ptr)))

  (func $info (param $ptr i32)
    (call $log (i32.const 2) (local.get $ptr) (call $len (local.get $ptr))))

  (func (export "cordis_meta") (result i32)
    (call $write (i32.const 0) (call $len (i32.const 0)))
    (i32.const 0))

  (func (export "cordis_apply") (param i32) (result i32)
    (call $info (i32.const 256))
    (i32.const 0))

  (func (export "cordis_dispose")
    (call $info (i32.const 128))))
```

- `cordis_meta` writes `{"plugin":{"name":"hello"}}`: a plugin named `hello`, with no dependencies, injections or provisions. It returns `0`.
- `cordis_apply` ignores its input (it never `read`s the message) and logs `hello from wasm` at level `2` (info).
- `cordis_dispose` logs `goodbye from wasm`.
- There is no `cordis_call`, as the plugin provides no service.

Run it with `cargo run -p kardia -- examples/kardia.yml` and edit the greeting: `hmr` reloads the module in place, so the old instance logs its goodbye, then the new one logs your greeting.
