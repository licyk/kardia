The plan was carried out in phases, each closed by porting and passing the matching part of the TypeScript test suite. All phases are done; this page records them and every place where the result departs from the design or from Cordis.

## Implementation phases [#phases]

| Phase | Scope | Exit criteria |
|---|---|---|
| **0. Scaffold** | Workspace, crates, CI (fmt, clippy, test) | empty crates build |
| **1. Effects & store** | ids, `Root`/`Context`/`Scope`, `IdTable`, effect engine (`effect_sync`, `effect`, `EffectScope`, `EffectHandle`), `provide`/`try_get_live`, isolate/intercept overlays; root fiber only | `dispose.spec` ported and green |
| **2. Fibers & lifecycle** | `Plugin` trait, registry/runtimes, `FiberData`, target/committed views, refresh/reload/unload with inertia, two-level guard, failure, `update`/`restart`, instantiation cascade, `replace`, checked `get` (Algorithm 6), cycle warning | Phase-2 specs green; model-based property tests ([Testing](/docs/development-testing#model-based)) green |
| **3. Services & built-ins** | `Service`/`Svc<S>` caller attribution, interception merge, typed events + internal events, logger + exporters, `kardia-timer`, `kardia-logger-console` | Phase-3 specs green; example app with a provider/consumer pair and hot provider replacement |
| **4. Loader** | `EntryOptions`, validation, `EntryTree`/`EntryGroup`/`Group`, entry state machine, outer/inner fibers, catalog, managed realms + migration, write-back hooks, `loader` barrier; `kardia` binary bootstrapping a root with the loader | loader specs (minus expressions) green |
| **5. Include & fs** | `kardia-fs` watcher; `kardia-include` parse/journal/patch/sync/atomic write/locations; `kardia.yml` bootstrap identical to `core/bin.js` | include + fs specs green; editing `kardia.yml` live reconfigures a running app |
| **6. Ergonomics** | `kardia-macros`: `#[plugin]`/`#[service]` derive (NAME, inject tuples, extension traits), compile-time undeclared-access errors for typed deps; optional expression language | macro tests (trybuild) |
| **7. Dynamic modules (optional)** | `ModuleSource`, `ModuleGraph`, ported HMR reconcile; WASM backend prototype; dylib dev backend | `reconcile.spec` ported against an in-memory source |

Phases 1–3 deliver the paper's core library; 4–5 the paper's loader; 7 the paper's HMR.

<Callout type="info">
Names as they ended up: `try_get_live` is `live`, the root is created with `Context::new()` (there is no public `Root`), and the service derive is `#[derive(Service)]`. The example app of Phase 3 is `crates/kardia/examples/provider_consumer.rs` (`cargo run -p kardia --example provider_consumer`).
</Callout>

## Implementation status [#status]

All phases above are implemented in `crates/` (`cargo test --workspace`; `cargo run -p kardia -- examples/kardia.yml` boots an app from a watched config file).

Every case of every TypeScript spec has been ported, found already covered, or judged not applicable. The not-applicable cases test JavaScript or Node mechanics with no Rust counterpart:

- decorators, prototypes and Proxy-based callable services, `this` binding;
- waterfall and the deprecated `dispatch` API;
- Node module resolution and loader internals (`resolve`, `import`, `create`, `package-manager`, `loader-utils`);
- file URLs and Windows drive letters;
- JavaScript stack frames;
- concurrent reads of one async iterator.

kardia is published on crates.io as [`kardia`](https://crates.io/crates/kardia) and the nine `kardia-*` crates; the [releases](https://github.com/licyk/kardia/releases) list each version.

CI (`.github/workflows/ci.yml`) runs `cargo fmt --check`, clippy with warnings as errors, `cargo xtask arch` and the test suite on pushes and pull requests that change Rust code, on a pinned toolchain (Rust 1.96.0), because the compile-error snapshots of `kardia-macros` change with the compiler. Pushing a `v*` tag runs `release.yml`: it reuses CI's run of the tagged commit, then runs `cargo publish --workspace` for every crate version crates.io does not have yet, waiting out its limit on new crates, and creates the GitHub release. The workflow can also be started by hand to resume a release that stopped part-way. [Contributing](/docs/development-contributing#releases) describes the workflows step by step.

## Deviations [#deviations]

Where the implementation departs from this plan or from the TypeScript code. Three entries are long and have their own subsections below the table.

| Topic | Implementation |
|---|---|
| Retired providers | Found by the [property tests](/docs/development-testing#model-based): retiring a fiber unbinds its live provisions at once, so a successor can provide in the same realm while old consumers still drain (they read through their committed views). The TS code keeps the slot until the drain and fails the successor. |
| Stale loads | A retired fiber's load still in flight may register inverses (so nothing it acquired leaks), but not provisions. |
| Provision removal during a drain | Postponed to the end of the provider's drain, so descendants can reach inherited services during their own cleanup without relying on microtask order. |
| Re-pointable contexts | Scope nodes carry their fiber; the fiber chain of an access is read off the derivation chain, so moving an entry also moves the fibers below it (the TS prototype behaviour). Entry tables are mutable `Overlay` nodes. |
| Checked typed access | `Injected<D>::get::<S, _>()` (the `_` is the inferred position of `S` in `D`); an undeclared `S` does not compile. |
| Expressions | A side-effect-free JavaScript subset (`kardia_loader::expr`) over JSON views of services; no function calls. |
| Errors | Config-file errors and loader-logged entry errors carry `file:line:col` locations as text. See [Errors](/docs/development-status#errors). |
| Loader API | Resolving a parent group waits for a group entry whose plugin is still loading (its group exists only once its `apply` runs). |
| Service-to-service calls | A service resolves its own dependencies through the context it stored (its definition site), so interception metadata of the outer caller does not reach the services it calls in turn (it stays on `Svc::caller()`), and effects a service creates through its stored context belong to the service's fiber. In TS, both follow the use site. |
| Events | `emit` logs a panicking listener and continues; TS lets a throwing listener abort the dispatch. There is no generic `waterfall`; typed hooks (`on_config`, `on_update`) replace it. |
| Logger | Messages are formatted by the caller (`impl Display`), so exporters receive finished text: no `%`-directives or custom formatters. |
| Loader hooks | `loader/patch-context` is `Loader::on_patch_context(ctx, hook)`; `EntryHandle::init`; an hmr case without a Rust counterpart. See [Loader hooks](/docs/development-status#loader-hooks). |
| Model tests | The [property tests](/docs/development-testing#model-based) drive real tokio schedules with random delays rather than a deterministic scheduler. They check ordering during every run, and preservation, recovery exactness and confluence (the active fibers are exactly the support set) at quiescence. |
| Dynamic modules | `ModuleSource` / `ModuleGraph` / `Hmr`, three file backends (WASM, dylib, process) sharing one JSON guest ABI, the `kardia-guest` SDK and watch mode. See [Dynamic modules](/docs/development-status#dynamic-modules). |

### Errors [#errors]

Parse and validation errors of config files carry `file:line:col`.

Errors the loader logs for an entry (option and config validation, `ModuleNotFound`, expression failures) are located through `TreeBackend::locate` / `locate_expr`:

- each issue gets `(at path, file:line:col)`;
- an expression failure gets an `at <path> (file:line:col)` frame;
- the entry and each ancestor that has a position get an `at <id> (file:line:col)` frame,

as text instead of rewritten JS stacks.

The include locates values where their owner writes them (its file, or a patch in its parent's file), aliases at their anchors, expression chars through YAML escapes. Values changed at runtime are not located. `Entry::evaluate` is not exposed.

### Loader hooks [#loader-hooks]

The `loader/patch-context` waterfall is `Loader::on_patch_context(ctx, hook)`: a hook gets the entry and the rest of the chain as a future, which builds the rest only when awaited; hooks run in registration order inside the loader's own isolation step and are removed with `ctx`'s fiber. Unlike TS, the new isolation table is installed together with the re-parenting at the end of the chain, not before the hooks run.

`EntryHandle::init` starts an entry or joins its pending start.

The hmr `index` case "waits for a second re-enable init" has no hmr decision to wait on in Rust (the transaction has decided once the held unload completes); its port guards that the re-enables leave one live instance and hmr adds no apply.

### Dynamic modules [#dynamic-modules]

`ModuleSource` / `ModuleGraph` / `Hmr`, plus three file backends that share one JSON guest ABI (documented in the `kardia-hmr` crate docs) and a bridge plugin instantiating the guest per fiber.

| Backend | How it works |
|---|---|
| `WasmSource` | Runs core WASM modules on wasmtime, one store per fiber, instead of WIT components, so guests need no component toolchain (the tests are written in WAT). |
| `DylibSource` | Speaks a C ABI instead of passing Rust types: a cdylib carries its own copies of `kardia-core` and tokio, with separate statics and no runtime context. Each version is loaded from a unique copy and never unloaded. |
| `ProcessSource` | Runs executables, one child process per fiber, speaking the same ABI as JSON lines over stdin and stdout (respawn = reload; a crashing guest fails only its own calls, and a guest that breaks the protocol is killed). There is no separate broker service: each fiber's `GuestService` is the RPC endpoint. |

Like the other backends, the process backend's calls are synchronous rather than the asynchronous RPC contract of [paper §6.2](/docs/concepts-related-work): they block the caller until the guest answers, so a hung guest blocks it too. The `kardia` binary chooses a backend by file extension and does not load process guests.

Guest services are JSON views with JSON calls (`GuestService`). `kardia-guest` is the Rust guest SDK: a `Guest` trait and `export!`, which emits the WASM exports on wasm32 and the C symbols elsewhere, so one source builds for both backends.

Watch mode (`HmrConfig { base, watch: { enabled, files, debounce } }`) follows the TS code: it watches `base` through `fs` and reloads each debounce window as one batch, one batch at a time. The files of failed imports are retried with the next batch, and changes to host modules are only reported. `base` resolves against the directory of the config file of the hmr entry, as the TS code does with `ctx.baseUrl`, or else against the working directory.

The `kardia` binary registers `hmr` and resolves any entry name that is not a built-in plugin as a guest module relative to the config file: `examples/kardia.yml` hot-reloads `plugins/hello.wat`.

For using guests, see [Guest plugins](/docs/guide-guests) and [Hot reload](/docs/guide-hot-reload).

## The TypeScript side [#typescript]

`js/` holds the npm packages `@kardiajs/core`, `@kardiajs/timer`, `@kardiajs/bridge`, `@kardiajs/tauri` and `@kardiajs/vue`, and `crates/kardia-bridge` the Rust host of the bridge ([TypeScript and Tauri](/docs/guide-typescript)). They are versioned and released apart from the crates ([Contributing](/docs/development-contributing#npm-releases)).

`@kardiajs/core` ports Kardia's core (its state machine, checked access, effect engine and logger), not the TypeScript Cordis code. It does not depend on Cordis, at run time or in development: this repository never did (`cordis/` is a local, gitignored copy for reference), and the packages have no runtime dependencies. Its test suite ports the relevant Cordis specs. Where it differs:

| Topic | `@kardiajs/core` |
|---|---|
| Service access | `ctx.get(key)` / `ctx.live(key)` instead of property access through a `Proxy` context. A plugin defined with `definePlugin` gets a context typed by its `inject`, so an undeclared access is a type error (Kardia's `Injected<D>`). |
| Caller attribution | A `Service` comes back from `ctx.get` as a view whose `caller` is the accessing context (Kardia's `Svc::caller`). Views are `Proxy` objects, so a service's `#private` fields do not pass through them; use `private`. |
| `apply` | May return a promise, or a function that runs when the plugin stops (as in Cordis; Kardia's `apply` returns only its result). Classes are instantiated per fiber; there is no `Service.init`. |
| Effects | `ctx.effect(scope => ...)` with `scope.defer`, `scope.adopt` and `scope.checkpoint`, or a returned disposer (Kardia's `effect_sync` / `effect` in one). No generator or async-iterator effects. |
| Internal events | `internal/plugin-inserted` and `internal/plugin-removed` (Kardia's `PluginInserted` / `PluginRemoved`) instead of Cordis' single `internal/plugin`; `internal/status` passes the old and new state. |
| Events | As in Kardia: `emit` logs a failing listener and runs the rest; no `waterfall`; update hooks are `ctx.onUpdate`. No decorators, no `this` binding of listeners. |
| `update` / `restart` | Throw at once for an invalid config or a retired fiber (Kardia's `Result`); the promise they return, which settles with the fiber, is marked handled, so dropping it never raises an unhandled rejection. |
| `ctx.inject(deps, apply)` | Creates a plugin of its own on every call, so `registry.replace` cannot target it. |
| Names | A fiber keeps its plugin's name after its last fiber is retired, so the events of its removal still name it. |
| Loader, include, HMR | Not ported: they read files, and the client runs in a webview. Vite's HMR can drive `registry.replace`. |

The bridge's calls are asynchronous, unlike the guest ABI's ([Dynamic modules](#dynamic-modules)): it is the asynchronous contract of paper §6.2. Its end-to-end tests drive the real Rust host from the TypeScript client.
