kardia is developed at [github.com/licyk/kardia](https://github.com/licyk/kardia). This page covers the Rust workspace, its CI and releases, and this documentation site.

<Callout type="info">
The repository's [`AGENTS.md`](https://github.com/licyk/kardia/blob/main/AGENTS.md) has the code rules. In short: breaking refactors are allowed, with no compatibility layers; validate external data once, at the boundary, and tolerate unknown fields; no complexity for speculative races or edge cases without agreement first; keep main functions on the normal flow, with details in small helpers below; comment only non-obvious constraints; regenerate generated files instead of editing them; test the real implementation with few mocks; follow the repository's existing tools and workflows; extract a function only when it is reused, complex or a nameable concept.
</Callout>

## Building and testing [#building]

```sh
cargo test --workspace          # the WASM guest test needs the wasm32-unknown-unknown target
cargo clippy --workspace --all-targets
cargo fmt --all
cargo xtask arch                # lib.rs and mod.rs only declare and re-export modules
```

- The WASM guest test builds its fixture as a WebAssembly module, so install the target first: `rustup target add wasm32-unknown-unknown`.
- Some tests build fixture crates with cargo while they run, so the first run takes a little longer.
- The minimum supported Rust version of the crates is 1.85 (`rust-version` in the workspace `Cargo.toml`); CI uses a pinned, newer toolchain (below).
- How the tests are organised, and which runtime each suite uses, is on [Testing](/docs/development-testing).

## Repository tasks: `cargo xtask` [#xtask]

The `xtask` crate (`xtask/`, a workspace member that is never published) holds the repository's own tasks; `.cargo/config.toml` makes them `cargo xtask <command>`.

| Command | What it does |
|---|---|
| `cargo xtask arch` | Checks the module structure: every `lib.rs` and `mod.rs` (in `crates/*/src`, `crates/*/tests` and `xtask/src`) only declares modules, re-exports, and holds docs and attributes. Implementation (functions, types, traits, `impl` blocks, constants, statics, `macro_rules!`, inline test modules) lives in a file of its own, re-exported from the entry file. Inline modules that only re-export (such as `kardia::prelude`) and proc-macro entry points, which Rust requires at the crate root, are allowed. It lists each violation with its file, line and kind, and fails if there is any. CI runs it. |
| `cargo xtask version <patch\|minor\|major> [--dry-run]` | Bumps the workspace version (`0.1.3` → `0.1.4` / `0.2.0` / `1.0.0`) in `[workspace.package]`, in the `kardia-*` entries of `[workspace.dependencies]`, and in `Cargo.lock`. When the requirement users write changes (a minor or major bump before 1.0, a major bump after), it also updates the `kardia = "0.x"` snippets of the README and these docs. It does not commit. |
| `cargo xtask tag [--version X.Y.Z \| --name NAME] [--message TEXT] [--push] [--remote NAME] [--dry-run]` | Creates an annotated tag on `HEAD`: `v<workspace version>` by default. `--version` must equal the workspace version (a `v*` tag releases it), and `--name` creates any other tag. It refuses an uncommitted working tree and a tag that already exists, locally or (with `--push`) on the remote. `--push` pushes the tag (to `origin`, or `--remote`). |

## CI [#ci]

The repository has three workflows, each for one part of it, so that a change runs only the checks it needs and a release tests a commit once.

| Workflow | Runs on | Does |
|---|---|---|
| `ci.yml` (Rust) | pushes to `main` and pull requests, except changes only to `site/`, Markdown, `LICENSE`, `NOTICE` and the hosting files; manual runs; called by Release | fmt, clippy, `cargo xtask arch`, the test suite |
| `site.yml` (docs) | pushes to `main` and pull requests that change `site/`; manual runs | the site's types, tests and build; outside pull requests, the deploy (below) |
| `release.yml` | `v*` tags; manual runs | publishes to crates.io (below) |

CI's steps:

1. Check out the repository.
2. Install Rust **1.96.0** (`dtolnay/rust-toolchain@1.96.0`) with `rustfmt`, `clippy` and the `wasm32-unknown-unknown` target. The toolchain is pinned because the compile-error snapshots of `kardia-macros` (trybuild tests) depend on the compiler version.
3. Restore the cargo cache (`Swatinem/rust-cache`).
4. `cargo fmt --all --check`
5. `cargo clippy --workspace --all-targets -- -D warnings`
6. `cargo xtask arch`
7. `cargo test --workspace`

A newer push cancels an older CI run of the same branch or pull request. Tags never start CI.

| A change to | Runs |
|---|---|
| a docs page (`site/`) | `site.yml` only |
| the README, `AGENTS.md`, the licence | nothing |
| Rust code, tests, `Cargo.*`, `xtask/`, a workflow other than `site.yml` | `ci.yml` |
| a version bump, then its tag | `ci.yml` once; `release.yml` reuses that run |

## Releases [#releases]

All crates share one version, `version` under `[workspace.package]` in the root `Cargo.toml` (the `[workspace.dependencies]` entries of the kardia crates carry it too).

<Steps>
<Step>
`cargo xtask version patch` (or `minor`, `major`), then commit and push: `git commit -am "chore(release): kardia 0.1.1"`, `git push`. The push runs CI.
</Step>
<Step>
`cargo xtask tag --push` tags the commit `v0.1.1` and pushes the tag, which starts `.github/workflows/release.yml`.
</Step>
<Step>
Release checks that the tag names the workspace version. It then finds CI's run of the tagged commit and waits for it if it is still running: a passed run is reused, a failed one stops the release. Only when there is no usable run (a commit CI never ran on, or a run a newer push cancelled) does Release call `ci.yml` itself as its checks. Each released commit is tested once.
</Step>
<Step>
It publishes every crate whose new version is not on crates.io yet, in dependency order (`cargo publish --workspace`; `xtask` is never published), then creates a GitHub release for the tag, with notes since the previous `v*` tag.
</Step>
</Steps>

The publish step is **resumable**:

- Before each attempt, it asks the crates.io API which `name@version` pairs already exist and excludes those crates, so a crate is never published twice.
- crates.io lets an account create only a few new crates at once and then one every ten minutes. When `cargo publish` fails with `429 Too Many Requests`, the workflow waits 610 seconds and tries again, up to eight attempts; any other failure fails the step. A release that adds new crates waits out this limit.
- The workflow can also be started by hand (`workflow_dispatch`) on a branch to resume a release that stopped part-way.
- It publishes with the `CARGO_REGISTRY_TOKEN` repository secret.

## Documentation site [#site]

This site lives in `site/`: [Fumadocs](https://fumadocs.dev) on TanStack Start (React), built with Vite and Tailwind CSS, with Bun as the package manager and script runner. It is outside the Cargo workspace, so `cargo` commands are unaffected.

```sh
cd site
bun install
bun run dev       # local server
bun run check     # TypeScript
bun run test      # Vitest
bun run build     # static output in site/.output/public
```

`bun.lock` is committed; `bun install --frozen-lockfile` installs exactly the locked versions, as the deployment workflow does.

### Content [#content]

- Pages are MDX files in `site/content/docs/`, with flat slugs grouped by prefix (`guide-*`, `concepts-*`, `reference-*`, `development-*`).
- The site is bilingual. Chinese is the default language: `<slug>.mdx`, served without a prefix. English is `<slug>.en.mdx`, served under `/en/`. Every page exists in both languages, and a test checks it.
- The sidebar order and its section headings come from `meta.json` (Chinese) and `meta.en.json` (English). Both must list the same slugs in the same order; a test checks that too.
- Links between pages use `/docs/<slug>` (the site adds `/en` itself). Besides Fumadocs' defaults, pages can use the `Cards`, `Callout`, `Steps`, `Tabs`, `Accordions` and `Mermaid` components without imports.
- Code, identifiers, configuration examples and the paper's notation stay as they are in both languages.

### Deployment [#deployment]

`.github/workflows/site.yml` checks and deploys the site; Rust's checks do not run for a docs-only change. A pull request that touches `site/` gets the types, tests and build. A push to `main` that touches `site/` also builds the site with `VITE_BASE_PATH=/kardia/` and publishes the output to the `gh-pages` branch (with the `GITEE_RSA_PRIVATE_KEY` deploy key), which GitHub Pages serves at **[https://licyk.github.io/kardia/](https://licyk.github.io/kardia/)**. Deploys run one at a time.

The base path is only for GitHub Pages, which serves the site under `/kardia/`; without `VITE_BASE_PATH`, the build serves from `/`.
