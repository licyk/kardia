状态与偏离

kardia 的实现阶段及其退出标准、实现状态，以及实现偏离计划或 TypeScript 代码的每一处。

计划按阶段执行，每个阶段以移植并通过 TypeScript 测试套件中对应的部分作为结束。所有阶段均已完成；本页记录这些阶段，以及结果偏离设计或 Cordis 的每一处。

实现状态

上述所有阶段都已在 crates/ 中实现（cargo test --workspace；cargo run -p kardia -- examples/kardia.yml 会从一个受监视的配置文件启动应用）。

每个 TypeScript spec 的每个用例都已移植、确认已被覆盖，或判定为不适用。不适用的用例测试的是没有 Rust 对应物的 JavaScript 或 Node 机制：

  • 装饰器、原型和基于 Proxy 的可调用服务、this 绑定；
  • waterfall 和已弃用的 dispatch API；
  • Node 模块解析与加载器内部（resolve、import、create、package-manager、loader-utils）；
  • 文件 URL 与 Windows 盘符；
  • JavaScript 栈帧；
  • 对同一个异步迭代器的并发读取。

kardia 已在 crates.io 上以 kardia 和九个 kardia-* crate 的形式发布；各版本见 Releases。

CI（.github/workflows/ci.yml）在改动 Rust 代码的推送和拉取请求上，在固定的工具链（Rust 1.99.1）上运行 cargo fmt --check、将警告视为错误的 clippy、cargo xtask arch 以及测试套件，因为 kardia-macros 的编译错误快照会随编译器而变化。推送 v* 标签会运行 release.yml：复用 CI 对该标签所指提交的运行结果，然后对 crates.io 上尚不存在的每个 crate 版本执行 cargo publish --workspace，并等待 crates.io 对新 crate 的数量限制过去，最后创建 GitHub Release。该工作流也可以手动启动，以继续一次中途停止的发布。参与开发逐步描述了这些工作流。

偏离

以下是实现偏离本计划或 TypeScript 代码之处。其中三项较长，在表格下方各有一个小节。

主题实现
已退役的提供者由属性测试发现：退役一个纤程会立即解除其存活的提供，因此后继者可以在同一领域中提供服务，而旧的消费者仍在排空（它们通过自己的已提交视图读取）。TS 代码会一直保留该槽位直到排空结束，并使后继者失败。
过期的加载已退役纤程仍在进行中的加载可以注册逆操作（因此它获取的任何东西都不会泄漏），但不能注册提供。
排空期间移除提供推迟到提供者排空结束时，这样后代在自身清理期间仍能访问继承的服务，而无需依赖微任务的顺序。
可重新指向的上下文作用域节点携带其纤程；一次访问的纤程链从派生链上读出，因此移动一个条目也会移动它下面的纤程（TS 原型的行为）。条目表是可变的 Overlay 节点。
带检查的类型化访问Injected<D>::get::<S, _>()（_ 是 S 在 D 中被推断出的位置）；未声明的 S 无法通过编译。
表达式一个无副作用的 JavaScript 子集（kardia_loader::expr），作用于服务的 JSON 视图；不支持函数调用。
错误配置文件错误和加载器为条目记录的错误以文本形式携带 file:line:col 位置。见错误。
加载器 API解析父分组时，会等待插件仍在加载中的分组条目（它的分组只有在其 apply 运行后才存在）。
服务间调用服务通过它保存的上下文（它的定义处）解析自己的依赖，因此外层调用者的拦截元数据不会传到它进一步调用的服务（这些元数据保留在 Svc::caller() 上），而服务通过其保存的上下文创建的效应属于该服务的纤程。在 TS 中，二者都跟随使用处。
事件emit 和 bail 记录发生 panic 的监听器并继续，serial 把该 panic 作为错误返回，parallel 收集它（见派发）；TS 让抛出异常的监听器中止分发。没有通用的 waterfall；由带类型的钩子（on_config、on_update）代替。
日志器消息由调用者格式化（impl Display），因此导出器收到的是已完成格式化的文本：没有 % 指令，也没有自定义格式化器。
加载器钩子loader/patch-context 即 Loader::on_patch_context(ctx, hook)；EntryHandle::init；一个没有 Rust 对应物的 hmr 用例。见加载器钩子。
模型测试属性测试以带随机延迟的真实 tokio 调度驱动，而不是确定性调度器。它们在每次运行期间检查顺序性，并在静止时检查保持性、恢复精确性和合流性（活跃纤程恰好是支撑集）。
动态模块ModuleSource / ModuleGraph / Hmr，三个共享同一套 JSON 访客（guest）ABI 的文件后端（WASM、dylib、进程），kardia-guest SDK 以及监视模式。见动态模块。

错误

配置文件的解析错误和校验错误携带 file:line:col。

加载器为某个条目记录的错误（选项与配置校验、ModuleNotFound、表达式失败）通过 TreeBackend::locate / locate_expr 定位：

  • 每个问题得到 (at path, file:line:col)；
  • 表达式失败得到一个 at <path> (file:line:col) 帧；
  • 条目以及每个有位置的祖先各得到一个 at <id> (file:line:col) 帧，

它们以文本形式给出，而不是改写 JS 栈。

include（配置文件引入）在值的所有者写下它们的地方定位这些值（所有者的文件，或其父级文件中的一个补丁），别名定位到其锚点，表达式中的字符穿过 YAML 转义定位。运行时更改的值不会被定位。Entry::evaluate 未公开。

加载器钩子

loader/patch-context waterfall 即 Loader::on_patch_context(ctx, hook)：钩子接收条目，以及以 future 形式表示的链的其余部分，这个 future 只有在被 await 时才会构建其余部分；钩子在加载器自身的隔离步骤中按注册顺序运行，并随 ctx 的纤程一起移除。与 TS 不同，新的隔离表与链末尾的重新设定父级一起安装，而不是在钩子运行之前安装。

EntryHandle::init 启动一个条目，或者加入它尚未完成的启动。

hmr 的 index 用例“waits for a second re-enable init”在 Rust 中没有可等待的 hmr 决定（被挂起的卸载完成时，事务已经做出决定）；它的移植版本检查重新启用之后只留下一个存活实例，且 hmr 不会额外执行 apply。

动态模块

ModuleSource / ModuleGraph / Hmr，加上三个共享同一套 JSON 访客 ABI（记录在 kardia-hmr crate 文档中）的文件后端，以及一个为每个纤程实例化访客的桥接插件。

后端工作方式
WasmSource在 wasmtime 上运行核心 WASM 模块（每个纤程一个 store），而不是 WIT 组件，因此访客不需要组件工具链（测试用 WAT 编写）。
DylibSource使用 C ABI，而不是传递 Rust 类型：cdylib 带有自己的一份 kardia-core 和 tokio，有独立的静态变量，也没有运行时上下文。每个版本都从一份唯一的副本加载，且永不卸载。
ProcessSource运行可执行文件，每个纤程一个子进程，通过 stdin 和 stdout 上的 JSON 行使用同一套 ABI（重新启动进程 = 重载；崩溃的访客只会使它自己的调用失败，破坏协议的访客会被杀死）。没有单独的代理服务：每个纤程的 GuestService 就是 RPC 端点。

与其他后端一样，进程后端的调用是同步的，而不是论文 §6.2 中的异步 RPC 约定：它们会阻塞调用者直到访客应答，因此挂起的访客也会阻塞调用者。kardia 二进制按文件扩展名选择后端，并且不加载进程访客。

访客服务是带 JSON 调用的 JSON 视图（GuestService）。kardia-guest 是 Rust 访客 SDK：一个 Guest trait 和 export!，后者在 wasm32 上生成 WASM 导出，在其他平台上生成 C 符号，因此同一份源码可以为两种后端构建。

监视模式（HmrConfig { base, watch: { enabled, files, debounce } }）遵循 TS 代码：它通过 fs 监视 base，把每个防抖窗口内的变化作为一批重载，每次只处理一批。导入失败的文件会随下一批重试，而宿主模块的变化只会被报告。base 相对于 hmr 条目所在配置文件的目录解析（与 TS 代码使用 ctx.baseUrl 的方式相同），没有配置文件时则相对于工作目录解析。

kardia 二进制注册了 hmr，并把任何不是内置插件的条目名称解析为相对于配置文件的访客模块：examples/kardia.yml 会热重载 plugins/hello.wat。

关于如何使用访客，见访客插件和热重载。

TypeScript 一侧

js/ 中是 npm 包 @kardiajs/core、@kardiajs/timer、@kardiajs/bridge、@kardiajs/tauri 和 @kardiajs/vue，crates/kardia-bridge 是桥的 Rust 宿主端（TypeScript 与 Tauri）。它们与 crate 分开版本化和发布（参与开发）。

@kardiajs/core 移植的是 Kardia 的核心（状态机、带检查的访问、效应引擎与日志器），而不是 TypeScript Cordis 的代码。它在运行时和开发时都不依赖 Cordis：本仓库从未依赖过（cordis/ 是被 gitignore 的本地参考副本），这些包也没有任何运行时依赖。它的测试套件移植了 Cordis 中相关的 spec。不同之处：

主题@kardiajs/core
服务访问使用 ctx.get(key) / ctx.live(key)，而不是通过 Proxy 上下文的属性访问。用 definePlugin 定义的插件得到一个按其 inject 定型的上下文，因此访问未声明的服务是类型错误（对应 Kardia 的 Injected<D>）。
调用者归属ctx.get 返回的 Service 是一个视图，其 caller 是发起访问的上下文（对应 Kardia 的 Svc::caller）。视图是 Proxy 对象，服务的 #private 字段无法穿过它；请使用 private。
apply可以返回 promise，或返回一个在插件停止时运行的函数（与 Cordis 相同；Kardia 的 apply 只返回结果）。类按纤程实例化；没有 Service.init。
效应ctx.effect(scope => ...)，配合 scope.defer、scope.adopt 和 scope.checkpoint，或返回一个撤销函数（相当于 Kardia 的 effect_sync / effect 合一）。没有生成器或异步迭代器形式的效应。
内部事件使用 internal/plugin-inserted 和 internal/plugin-removed（对应 Kardia 的 PluginInserted / PluginRemoved），而不是 Cordis 的单个 internal/plugin；internal/status 同时传递旧状态和新状态。
事件与 Kardia 相同：emit 记录失败的监听器并继续运行其余监听器；没有 waterfall；更新钩子是 ctx.onUpdate。没有装饰器，也不绑定监听器的 this。
update / restart配置无效或纤程已退役时立即抛出（对应 Kardia 的 Result）；它们返回的 promise 随纤程一起结算，并被标记为已处理，因此丢弃它不会引发未处理的拒绝。
ctx.inject(deps, apply)每次调用都创建一个独立的插件，因此 registry.replace 无法指向它。
名称纤程在其插件的最后一个纤程退役后仍保留插件名称，因此移除时的事件仍带有该名称。
加载器、include、HMR未移植：它们读取文件，而客户端运行在 webview 中。Vite 的 HMR 可以驱动 registry.replace。

与访客 ABI（动态模块）不同，桥的调用是异步的：这正是论文 §6.2 中的异步约定。它的端到端测试从 TypeScript 客户端驱动真实的 Rust 宿主。
